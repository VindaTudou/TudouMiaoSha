# V0.1 丢失更新（Lost Update）

> 目的：在写任何业务代码之前，亲手看见"并发写同一个值"会出错。
> 这是秒杀超卖的**同一个 bug**，只是发生在内存里而不是数据库里。

## ⚠️ 更正记录（2026-11-02）

这份文档的第一版有一个错误，记录下来比抹掉它更有价值。

**事故**：我把 `100 线程 × 1000 次`（默认参数）和 `100 线程 × 20000 次` 的两组数据
当成了同一个实验的前后对比，得出"volatile 把丢失率从 73.7% 降到 35.8%"的结论。

**实际观测**：

| 谁 | 命令 | naive 丢失 | volatile 丢失 |
|---|---|---|---|
| 学习者 | `java NaiveCounter.java`（默认 100×1000） | ≈ 2,000 | ≈ 15,000 |
| 我 | `java NaiveCounter.java 100 20000` | ≈ 1,200,000 | ≈ 925,000 |

两个数字都真实，但**不是同一个实验**。差 25 倍的原因是每线程迭代次数不同。

**根因（两个，第二个更严重）**：

1. `VolatileCounter` 没把线程数和迭代次数打印出来，两组实验长得一模一样，肉眼无法区分。
2. 丢失率本身**极不稳定**（实测 0% ~ 91%），所以"35.8%"这种精确到小数的数字，
   本来就不该被当作结论引用。

**修复**：

1. 所有程序必须打印完整参数（线程数、每线程次数、期望值）。
2. 统一入口 `run-all.sh`，参数写死在脚本里，不再手工拼命令。
3. 结论从"丢失率多少"改写为"**是否为 0**"——这才是稳定的。

> 教训：**不写清参数的压测，等于没做。**
> 同一个程序、同一个参数，两次运行能差 25 倍——这就是为什么
> BENCHMARK.md 的每一行都必须带配置和 commit。

## 实验环境

| 项 | 值 |
|---|---|
| 机器 | Apple M2，8 核，16 GB |
| JDK | Temurin 17.0.18 |
| 日期 | 2026-11-02 |
| 代码 | `NaiveCounter` / `VolatileCounter` / `AtomicCounter` / `SyncCounter` |
| 标准入口 | `bash run-all.sh`（默认 100 线程 × 20000 次 × 5 轮） |

## 实验一：同一份工作，四种写法

标准配置：100 线程 × 20000 次 = 2,000,000 次自增，5 轮取中位，JIT 开启。

| 实现 | 实际结果 | 丢失率 | 中位耗时 | 正确 |
|---|---|---|---|---|
| `NaiveCounter`（无保护） | 799,734 | **60.01%** | 12 ms | ❌ |
| `VolatileCounter`（volatile） | 1,069,069 | **46.55%** | 100 ms | ❌ |
| `AtomicCounter`（CAS） | 2,000,000 | 0% | 72 ms | ✅ |
| `SyncCounter`（synchronized） | 2,000,000 | 0% | 248 ms | ✅ |

**读法**：前两行永远不为 0，后两行永远是 0。这个差别在所有配置下都成立。

## 实验二：丢失率极不稳定（本实验最重要的部分）

同一个 `NaiveCounter`，只改参数或 JVM 模式：

| 配置 | Naive 丢失率 | Volatile 丢失率 |
|---|---|---|
| 100 × 1000（JIT） | 1.9% – 4.7% | **0% – 26%** |
| 100 × 20000（JIT） | 60% | 47% |
| 100 × 20000（`-Xint`） | 67.5% | 80.6% |
| 100 × 200000（JIT） | 13% – 91% | 38% – 91% |
| **Atomic / Sync（任意配置）** | **0%** | **0%** |

看第二行最后一列：`volatile` 有时一次都不丢，有时丢 26%。

看 `-Xint` 那行：`volatile` 的丢失率反而**高于** naive——和 JIT 下的方向相反。

**为什么**：丢失率取决于"读和写之间那道缝有多宽"和"有多少人同时挤在缝里"，
而这两者受 JIT 优化、线程启动错开、每次迭代耗时共同影响。它是一个**受十几个因素影响的观测值**，
不是一个可以引用的小数。

**能引用的结论只有一个**：错误实现**永远不为 0**，正确实现**永远是 0**。

## 实验三：证据——`count++` 不是一步

`javap -c` 反编译自增循环：

```
7: getstatic   count   // ① 把 count 读到寄存器
10: iconst_1           // ② 常量 1
11: iadd              // ③ 相加
12: putstatic  count   // ④ 写回内存
```

四条字节码、两次内存访问。三个线程可能同时执行 ① 读到同一个值（比如 100），
各自加 1 写回 101 —— 三次自增，只生效一次。

## 实验四：加 volatile 到底改了什么

| 维度 | 普通 `int` | `volatile int` |
|---|---|---|
| 读 | 可能读到寄存器/私有缓存里的旧值 | 强制从主存读 |
| 写 | 可能延迟刷回 | 立即刷回，并使其他核心缓存失效 |
| 读-改-写是否原子 | 否 | **仍然否** |
| 耗时（100×20000） | 12 ms | 100 ms（8 倍） |

`volatile` 保证**可见性**（写了别人看得见），不保证**原子性**（读改写不被打断）。

时序上，竞争发生在缝里：

```
时刻    线程 A                线程 B
 t1     读 count = 100
 t2                           读 count = 100      ← 两人都读到"最新值"
 t3     算 101
 t4                           算 101
 t5     写 count = 101
 t6                           写 count = 101      ← A 那次被覆盖
```

`volatile` 让 t1/t2 读到的是主存里最新的 100，但"最新"不等于"独占"。

**而且它的效果方向都不稳定**（实验二里 JIT 下降低丢失率、`-Xint` 下升高）。
一个让结果变得不可预测的修饰符，不能拿来当同步手段。

## 实验五：一次失败的实验设计

第一版扫描是"固定总工作量 10 万次，只改线程数"：

| 线程数 | 每线程次数 | 丢失率 |
|---|---|---|
| 10 | 10,000 | 62.9% |
| 100 | 1,000 | 3.7% |
| 400 | 250 | 0.3% |

看起来"线程越多越安全"——**结论是错的**。因为同时改了线程数和每线程次数两个变量，
真正起作用的是后者（竞争窗口长度）。压测里最经典的错误：**一次只改一个变量。**

## 实验六：竞争窗口越长，丢得越多

固定 100 线程，只改每线程次数（JIT）：

| 每线程次数 | 丢失率 |
|---|---|
| 500 | 0.57% |
| 5,000 | 25.90% |
| 20,000 | 46.11% |
| 50,000 | 29.36% |

500 次时整个程序 3 毫秒跑完，线程一个个启动、还没重叠就结束了。
**这直接解释了 V1 为什么必须压满 10 秒以上**——短促的压测测不出问题。

## 结论（修订版）

1. `count++` 是"读-改-写"三步，并发下不是原子操作，会丢失更新。
2. **丢失率不是一个稳定数值**（实测 0%~91%），不能引用具体小数；能引用的是"是否为 0"。
3. **并发正确性没有中间态**：丢 0.001% 和丢 90% 都是错的。
4. 没有保护的版本常常"看起来最快"，因为它少干了活。别拿错误代码的耗时当性能。
5. 修法只有两类：锁（串行化）和 CAS（重试）。代价不同，正确性相同。
6. `volatile` 只解决可见性，不解决原子性，效果方向还不稳定——**不要拿它做同步**。
7. 短任务测不出并发问题；压力要持续足够久。
8. 压测必须记录完整参数，否则实验不可复现。

## 映射到项目里

| 内存版（本实验） | 数据库版（V1 会踩到） |
|---|---|
| `count++` | `SELECT stock` → 判断 → `UPDATE stock` |
| 读-改-写三步 | 查-判断-写三步 |
| 丢失更新 | **超卖** |
| `synchronized` | 行锁 / `SELECT ... FOR UPDATE` |
| `AtomicInteger` | `UPDATE ... WHERE stock >= 1`（单语句原子） |
| `volatile` | 只读不写的状态位（例如活动开关） |

## 实验七：只要 2 个线程就开始丢

每线程 20000 次，各 3 轮：

| 线程数 | 丢失次数（3 轮） | 丢失率 |
|---|---|---|
| 1 | 0 / 0 / 0 | **0%** |
| 2 | 11,482 / 13,750 / 14,565 | ≈ 33% |
| 4 | 28,049 / 37,388 / 42,414 | ≈ 45% |

单线程不丢，**不是代码写对了，是没有人跟它抢**。同一份代码加一个线程就丢 1.2 万次。

> "单线程测试通过"不能作为并发安全的证据。这叫**碰巧正确**，不叫正确。

## 待你验证

1. ✅ `volatile` 救不了——见实验二/四。
2. ✅ 单线程不丢（实验七）；原因是无竞争，不是代码正确。
3. ✅ `AtomicCounter` 快于 `SyncCounter`：CAS 失败后不挂起、原地重试（自旋）；
   `synchronized` 抢不到锁会把线程挂起，等 OS 唤醒，多了上下文切换成本。
   代价反转：冲突极端激烈时 CAS 会空转烧 CPU，此时分段（如 `LongAdder`）才更优。
