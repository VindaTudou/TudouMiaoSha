# V0.3 + V0.4 基线测量

> V0.3：索引对执行计划和延迟的影响
> V0.4：单机热点行 TPS 基线 —— 这是后面所有容量估算的锚点
>
> **本次有一个预测被实测推翻了**，见第四、五节。保留错误比抹掉它更有价值。

## 环境

| 项 | 值 |
|---|---|
| MySQL | 8.4.5，容器 4 核 / 7.75 GiB，buffer pool 512 MB |
| 数据 | `product` 10 万行（`id=1` 为秒杀热点商品） |
| 隔离级别 | REPEATABLE READ |
| 持久化 | `sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`（默认，最安全） |
| 压测工具 | JDBC 直连（`HotspotBench.java`），长连接，autocommit |
| 复现 | `bash setup.sh` + `HotspotBench.java` |

## 一、索引对执行计划的影响

查询 `WHERE name = '商品-50000'`（10 万行中精确命中 1 行）：

| 条件 | `type` | `key` | `rows` | `Extra` | 实测耗时 |
|---|---|---|---|---|---|
| **无索引** | `ALL` | `NULL` | 99,806 | `Using where` | **26.3 ms** |
| 有索引 | `ref` | `idx_name` | 1 | — | **0.031 ms** |
| 有索引 + 覆盖索引 | `ref` | `idx_name` | 1 | `Using index` | **0.019 ms** |

**无索引比有索引慢约 850 倍。**

`EXPLAIN ANALYZE` 还暴露了一件事：`26.3 ms` 里有 `17.7 ms` 是"扫完 10 万行"，剩下 8.6 ms 是过滤和返回。

---

## 二、索引对 UPDATE 延迟的影响

同一条 `UPDATE product SET stock=stock WHERE name='商品-50000'`，单线程：

| 条件 | QPS | p50 | p95 | p99 |
|---|---|---|---|---|
| 无索引 | **33.6** | **29.74 ms** | 30.94 ms | 36.77 ms |
| 有索引 | **4,613.8** | **0.21 ms** | 0.30 ms | 0.49 ms |

**延迟差 142 倍，吞吐差 137 倍。**

> 这一条直接说明：**V1 的 `WHERE` 列没有索引，压测出来的数字全是垃圾。**
> 不是"慢一点"，是"慢两个数量级"。

## 三、热点行 TPS 基线（V0.4 的核心产出）

N 个连接并发执行同一条 UPDATE，全部打 `id=1` 这一行，库存设为 1e9 保证每次都成功：

| 线程数 | QPS | p50 | p95 | p99 |
|---|---|---|---|---|
| 1 | 1,504 | 0.60 ms | 0.99 ms | 1.41 ms |
| 4 | **2,103** | 1.78 ms | 2.65 ms | 3.38 ms |
| 8 | 2,004 | 3.79 ms | 5.31 ms | 6.43 ms |
| 16 | 1,919 | 8.41 ms | 10.40 ms | 12.60 ms |
| 32 | 2,225 | 14.00 ms | 16.90 ms | 19.88 ms |

### 这张表的读法

**① 吞吐在 ~2,000 TPS 封顶，从 4 线程开始就饱和了**

线程从 4 加到 32（8 倍），QPS 只从 2,103 变到 2,225（+6%）。

**② 延迟随并发线性上涨**

```
p50:  0.60 → 1.78 → 3.79 → 8.41 → 14.00 ms
线程:   1      4      8      16      32
```

**并发每翻一倍，延迟大致翻一倍，吞吐不动。** 这是**饱和**的标准签名——

> 用排队论的话说（Little's Law）：`并发数 = 吞吐 × 延迟`。
> 吞吐不变时，加人只会让队伍变长，不会让门变宽。

**③ CPU 只有 30%**

压测期间采样：

```
CPU=29.34%  内存=704.8MiB / 7.749GiB
CPU=30.87%
CPU=29.72%
CPU=29.32%
CPU=30.90%
```

**CPU 低 + 延迟高 = 系统没在算，在等。**

## 四、预测被推翻：库存耗尽后，吞吐反而**升高**

### 我原本的预测

> "库存扣到 0 之后，所有人还在抢同一把锁，只是抢到了发现不能买。
> 所以 QPS 不会回升，会出现平台期。"

### 实测结果

把 `id=1` 的库存设为 0，所有 UPDATE 都影响 0 行：

| 线程数 | 库存充足（影响 1 行） | 库存为 0（影响 0 行） | 倍数 |
|---|---|---|---|
| 1 | 1,504 | **4,955** | **3.3×** |
| 4 | 2,103 | **14,252** | **6.8×** |
| 16 | 1,919 | **17,900** | **9.3×** |

**完全相反。卖完之后不但没有掉速，反而快了将近一个数量级。**

### 为什么

锁确实还在抢（V0.2 实验四已经证明：A 持锁时 B 会阻塞）。
**但"没有修改任何数据"的事务，在提交时无事可做。**

| | 影响 1 行 | 影响 0 行 |
|---|---|---|
| 定位行 + 加锁 | ✅ | ✅ |
| 写 undo log | ✅ | ❌ |
| 改内存页（标记脏页） | ✅ | ❌ |
| 写 redo log | ✅ | ❌ |
| 写 binlog + `fsync` | ✅ | ❌ |
| 提交开销 | **大** | **几乎为零** |

**锁还是那把锁，但每次占用它的时间从 ~0.6 ms 缩到 ~0.05 ms。**

## 五、瓶颈拆解：不是 CPU，是提交时的持久化

在库存充足的情况下，逐项关掉持久化（1 线程）：

| 配置 | QPS | p50 | 说明 |
|---|---|---|---|
| `sync_binlog=1` + `flush_log=1`（默认） | 1,504 | 0.60 ms | 每次提交 fsync binlog + redo |
| `sync_binlog=0` | 2,524 | 0.35 ms | 不 fsync binlog → **+68%** |
| `sync_binlog=0` + `flush_log=0` | 3,573 | 0.27 ms | 再省掉 redo fsync → 再 +42% |
| 不修改数据（库存 0） | 4,955 | 0.20 ms | 整条写路径都跳过 |

**结论：2,000 TPS 的天花板里，一大半是"保证不丢数据"的成本。**

这也解释了为什么加并发没用：**同一行的写必须串行，连提交时的 fsync 也一起串行**。
多线程无法把 fsync 合并掉，因为锁没释放之前下一个人进不来。

> 顺带排除了一个错误猜测：我一开始以为是 redo fsync 的问题，
> 单独把 `flush_log` 改成 0 几乎没变（1,504 → 1,568）。
> 真正的大头是 **binlog fsync**。**先测再改，不要凭直觉调参。**

## 六、结论

1. **索引让 UPDATE 快 142 倍**（29.74 ms → 0.21 ms）。这不是优化，是及格线。
2. **单机热点行写天花板 ≈ 2,000 TPS**（4 核容器 / 512 MB buffer pool / 默认持久化）。
3. **并发从 4 开始就饱和**，之后只增加延迟：`p50` 从 0.60 ms 涨到 14 ms。
4. **CPU 只有 30%** —— 瓶颈是串行等待，不是计算。
5. **库存耗尽后吞吐升高 9 倍**（原预测错误，见第四节）。
6. **瓶颈的主要成分是提交持久化**，binlog fsync 占大头。

## 七、对 V1 的意义

| 这一节的数字 | V1 会怎么用 |
|---|---|
| 2,000 TPS 单机热点天花板 | V1 压测的目标 QPS 就定在它附近，看能不能打到 |
| 并发 4 就饱和 | V1 的连接池不需要开大，10 个足够把锁打满 |
| CPU 30% + 延迟线性涨 | V1 的"瓶颈判断"标准：CPU 低就是等，不是算 |
| 索引 142 倍 | V1 任何 `WHERE` 列没索引，压测数字直接作废 |
| 库存 0 反而快 | V1 的成功率曲线会比 QPS 曲线更早"塌陷"——**必须分开统计** |
