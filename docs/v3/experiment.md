# V3 实验记录

> V2 的结论是：请求侧能扛 3,000/s，但**落库还是 950/s**，而且系统不知道自己几斤几两——
> 压力一大所有人一起变慢，依赖一挂就雪崩。
>
> V3 不追吞吐，做四件事：**先能看见（M1）→ 超载会拒绝（M2）→ 能扩（M3）→ 挂了能撑（M4）**。
>
> 顺序不能换：M2 的阈值要从 M1 的曲线里读出来，M4 的判定要看 M1 的指标。

# M1 · 可观测性：先给系统装上仪表盘

## 一、为什么这是第一步

V2 里为了搞清"37ms 花在哪"，我改了一次代码、跑了 6 轮压测、花了半小时，
最后只排除了一个嫌疑，还剩 30ms 不知道。

lag 多少？靠压测脚本里临时起 `for i in {1..300}; do lag; sleep 1; done`。
线程满没满？手动 `curl` 一下 actuator。
CPU 多少？`docker stats` 肉眼看。

**这些数据只在"我在压测"的时候存在，压测一停就没了。**
线上真出事，只有一堆日志。

## 二、装了什么，各自干什么

| 组件 | 一句话 | 干什么 |
|---|---|---|
| **Micrometer** | 应用内的台账 | 把 QPS、延迟、积压这些数字记下来，暴露成 `/actuator/prometheus` |
| **Prometheus** | 每 5 秒来抄一次账的人 | 定时抓取那个端点，存成带时间戳的序列（时序数据库） |
| **Grafana** | 画图 + 报警的 | 连 Prometheus，把序列画成曲线，配阈值告警 |

抓回来的原始数据长这样（纯文本，一行一个数字）：

```
miaosha_order_total{result="success"} 45231
miaosha_order_total{result="soldout"} 8812
tomcat_threads_busy_threads 12
kafka_consumer_fetch_manager_records_lag{partition="0"} 340
```

计数器只增不减，所以"每秒多少"要用两次采样的差值算——这就是 PromQL 里 `rate()` 干的事。

> **为什么不写脚本采**：脚本只在压测时有、不存历史、不能告警、多实例要自己拼。
> 脚本是体检，Prometheus 是心电监护仪。

## 三、埋了哪四个指标（这是重点，不是"装个监控"就完事）

Spring Boot 自带的 `http_server_requests` 只知道"这个 URL 花了多久"，
它不知道这一单是抢到了还是售罄、这 37ms 里 Redis 占多少、消费者落库成功了几单。

所以自己埋了四个：

| 指标 | 类型 | 埋在哪 | 回答什么问题 |
|---|---|---|---|
| `miaosha_order_total{result}` | Counter | `OrderService` | success / soldout / duplicate / **ratelimited** / send_fail / not_preheated 各多少 |
| `miaosha_redis_deduct_seconds` | Timer | `StockService.tryDeduct` | Lua 到底多快（V2 里那个"~0.1ms"是估的，没人量过） |
| `miaosha_kafka_send_seconds` | Timer | `OrderProducer.send` | **V2 那 5~6ms 的直接证据** |
| `miaosha_consumer_persist_total{result}` | Counter | `OrderConsumer` | ok / dup / short / bad_message / fail |

外加 Kafka 客户端的原生指标（`KafkaClientMetrics`），其中最重要的是：

```
kafka_consumer_fetch_manager_records_lag{partition="0"}   ← 还有多少单没落库
```

### 四个指标全部预注册

第一单还没发生的时候，这些计数器就以 0 出现在面板上。
不预注册的话，Grafana 上新实例的面板是空洞，很容易被误判成"没有流量"。

## 四、验证一：监控的数字，和已知答案对得上吗

这是**必须先做**的一步。一个标签写错、一次抓取失败、一个计数器名字打错，
面板上照样有漂亮的曲线，只是那条线是错的。

方法：拿一个已知答案去对——k6 说发了多少个请求，Prometheus 就应该数出多少个。

跑三次（3,000/s，30 秒）：

| 轮次 | k6 报的请求数 | Prometheus 计数差值 | 误差 |
|---|---|---|---|
| 1 | 89,353 | 89,353 | **0.00%** |
| 2（换 JVM） | 86,983 | 86,983 | **0.00%** |
| 3 | 87,947 | 87,947 | **0.00%** |

**三次全部一字不差。** 计数类指标可以信了。

> 复现：`make verify-metrics`

## 五、验证二：监控本身有没有拖慢系统

这个问题必须问。Prometheus 每 5 秒来序列化 1,666 行指标，
Grafana 还连着查，这些都是要花 CPU 的。

我先测到一版"监控开着 P99 115ms、关掉 17ms"，差点写成结论。
**但重跑一次，同样的配置是 17ms。** 说明那不是监控的锅。

真正的对照要在"每轮都干净"的前提下做：

| 场景 | QPS | P99（k6 客户端） | 丢弃 |
|---|---|---|---|
| 抓取**关**，排空后 | 2,999 | **17 ms** | 0 |
| 抓取**开**（5s 一次），排空后 | 2,996 | **18 ms** | 50 |
| 抓取**开**（5s 一次），排空后 | 3,000 | **13 ms** | 0 |

**结论：监控开销落在噪声里，测不出来。**

> 抓取一次耗时 17ms，5 秒一次 → 占用率 0.34%。如果这都能让 P99 涨 6 倍，
> 那说明系统本身离悬崖只有一步。真实原因见第七节。

## 六、踩到的四个坑（每个都会让面板"看起来正常其实在骗你"）

### 坑 1：`tomcat_threads_busy_threads` 根本不存在

装完监控，最关心的那条线程曲线是空的。原因是 **Spring Boot 3 默认关闭了 Tomcat 的 MBean 注册**，
而线程池指标是从 MBean 读的。

```yaml
server:
  tomcat:
    mbeanregistry:
      enabled: true     # 不开这个，就看不到线程池
```

**这条最阴**：不报错，不告警，只是那条线永远空白。

### 坑 2：`records_lag_max` 是 NaN

```promql
sum(kafka_consumer_fetch_manager_records_lag_max)   →  NaN
```

Kafka 在"还没有积压测量值"时把 `records-lag-max` 报成 NaN，一 `sum()` 全变 NaN，
排空判断逻辑直接死循环（我第一次跑就卡了 300 秒）。

真正能用的是**分区级**的：

```promql
sum(kafka_consumer_fetch_manager_records_lag)       →  75145   ✅
```

### 坑 3：`rate(...[15s])` 配 15 秒抓取 → 面板显示"无数据"

`rate()` 的窗口里至少要 2 个样本。窗口 15 秒、抓取 15 秒，
两个样本正好卡在窗口边界上，经常只落进 1 个 → 算不出来 → 空白。

**两个一起改**：抓取间隔降到 5 秒，查询窗口放到 30 秒以上。

### 坑 4：`lsof -ti :8080` 会把 Prometheus 一起杀掉

我想重启应用，执行 `kill $(lsof -ti :8080)`。
结果 Prometheus 也死了——因为它**正在抓取 8080**，那条连接也算在 `:8080` 上。

```
正确写法：lsof -ti tcp:8080 -sTCP:LISTEN
```

> 这个坑的价值：**"杀了该杀的"和"杀了正在用它的"是两件事。**

## 七、意外收获 1：延迟数字的方差大得吓人

同一份代码、同一个到达率 3,000/s、同样的配置，P99 测出来是这样的：

| 场景 | P99 |
|---|---|
| 新启动的 JVM | **243 ms** |
| 同一 JVM，累计处理 ~18 万单 | 123 ms |
| 同一 JVM，累计 ~26 万单 | 165 ms |
| 同一 JVM，累计 ~35 万单 | 52 ms |
| 已经跑了几十万单的老 JVM（V2 的样本） | **13 ~ 18 ms** |

**19 倍的差距，全部来自"这台 JVM 跑过多少请求"。**

还发现另一个更大的：**应用放进容器后**（Docker VM 只有 4 核，和 MySQL/Kafka 抢），
同样 3,000/s，P99 是 **1,488ms**、丢弃 6,237 次；放回宿主机立刻回到 **17ms**。

> 这两条合起来说明一件事：**这套环境的延迟数字，只能同 JVM、同部署形态下横向比。**
> 这也解释了 V2 里那些 P99 为什么忽高忽低——我们一直没控制"预热程度"这个变量。
>
> 对 M2 的影响：找"容量拐点"时，必须先跑一轮热身丢掉，再跑正式那轮。

## 七·补、补测：预热曲线到底有多长（5 轮同一 JVM）

上一节只说"冷 JVM 更差"，没说清"多冷、多久热"。补一个受控实验：

**重启 JVM → 连续跑 5 轮，每轮 20 秒、3,000/s，每轮开始前等 Kafka 积压排空。**

| 轮次 | 这台 JVM 累计处理订单 | P50 | P95 | P99 | QPS | 丢弃 |
|---|---|---|---|---|---|---|
| 1 | 1 | 15 ms | 182 ms | **313 ms** | 2,825 | 3,472 |
| 2 | 56,531 | 7 ms | 30 ms | **92 ms** | 2,944 | 1,100 |
| 3 | 111,907 | 5 ms | 30 ms | **83 ms** | 2,970 | 593 |
| 4 | 174,840 | 5 ms | 8 ms | **12 ms** | 3,000 | 0 |
| 5 | 234,843 | 4 ms | 7 ms | **11 ms** | 3,000 | 0 |

**读法：横轴不是时间，是"这台 JVM 一共干过多少活"。**

```
313ms ──► 92ms ──► 83ms ──► 12ms ──► 11ms ──► 稳态
 冷              预热中                    ≥17 万单后
```

**结论：这台 JVM 要跑 15~17 万单（约 60 秒满负荷）才进入稳态。**

前 3 轮的丢弃（3,472 / 1,100 / 593）也是同一个原因：
延迟高 → VU 被占住 → `constant-arrival-rate` 发不出足量请求 → k6 记成丢弃。
**所以"丢弃"在这里不是压测机不行，是被测系统真的慢。**

### GC 能解释多少

同一个 JVM 的 GC 日志（`logs/gc.log`）：

| 时间 | GC 次数 | 累计暂停 |
|---|---|---|
| **第 0 分钟** | **56** | **346 ms** |
| 第 1 分钟 | 20 | 82 ms |
| 第 2~4 分钟 | 17 | 82 ms |
| 第 5 分钟 | 25 | 63 ms |
| 第 6~9 分钟 | 42 | 98 ms |

- 单次最长 **62.8 ms**，平均 4.2 ms
- **第 0 分钟就占掉全程 GC 时间的一半**——堆在长、分配率在爬坡

**GC 能解释一部分尾延迟，但解释不了 313ms。**
主因更可能是 JIT 分层编译（解释执行 → C1 → C2）加上连接池/线程池的惰性建立。

> 本想用 `-Xlog:jit+compilation` 直接数编译事件，结果**日志是 0 字节**——
> 这个 tag 写法被 JVM 静默忽略，不报错。这是又一个"看着在监控，其实什么都没记"的坑。
> 下次改用 `-XX:+PrintCompilation`。

### 对压测方法的直接影响

1. **正式测量前必须热身一轮并丢弃**，否则第一轮的数字没有可比性。
2. 横向对比只能在同一预热程度下做——现在是"≥20 万单之后"。
3. 这也解释了 V2 那组 13~18ms 为什么稳定：app 当时已经连续跑了 50 万单以上。

> 这组数据也画成了图：[m1-report.html](m1-report.html) 图 1。

## 八、意外收获 2：所有消息只进了同一个分区

清积压时重置消费位点，看到这个：

```
PARTITION 0  NEW-OFFSET 1832506
PARTITION 1  NEW-OFFSET 0
PARTITION 2  NEW-OFFSET 0
```

**三个分区，两个是空的。**

因为生产者发消息用的 key 是 `productId`，而这次秒杀只有一个商品 → 同一个 key
永远哈希到同一个分区 → 另外两个分区一条消息都没有。

于是：**3 个消费者，只有 1 个在干活，另外 2 个空转。**

这条把 V2 的"消费速率 950/s"解释完整了：

| 原因 | 贡献 |
|---|---|
| MySQL 单行锁 + 事务 | 主要因素，和 V1-b 一样 |
| **消息全在一个分区 → 消费并行度 = 1** | 就算把 MySQL 换掉，也还是一个消费者在跑 |

> **对 V4 的影响**：分桶（把库存拆成 N 行）必须同时改分区 key（如 `productId-bucketId`），
> 否则加了消费者也没用。这是这条观测最值钱的地方。

## 九、M1 结论

**做成了什么**

| 项 | 结果 |
|---|---|
| 指标端点 | `/actuator/prometheus`，1,666 行 |
| 自定义指标 | 4 类，全部预注册 |
| Kafka 积压 | 分区级 lag，可用 |
| Grafana 面板 | 6 张图，自动加载（`ops/grafana/dashboards/miaosha.json`） |
| 告警规则 | 4 条（积压 > 1 万、发送失败率 > 1%、P99 > 500ms、线程满） |
| 计数准确性 | **3 次对账，误差 0.00%** |
| 监控自身开销 | 测不出（落在噪声里） |

**发现了什么**

1. 计数类指标完全可信；延迟类指标**方差极大**，必须先热身、且只能同环境比。
2. 部署形态（容器 vs 宿主机）对 P99 的影响是 **100 倍级**，这是 V2 数据的一个隐藏前提。
3. 单商品秒杀时 **Kafka 只有一个分区有数据**，消费并行度实际是 1。
4. 四个指标坑，其中"Tomcat MBean 默认关闭"最隐蔽。

**没解决的**

- 延迟方差的根因只定位到"JVM 预热程度"，没有更细的分解。
- 告警只做到 Prometheus 里能看到 firing，没接 Alertmanager（本地实验不需要）。
