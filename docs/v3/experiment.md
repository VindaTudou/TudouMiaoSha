# M1 · 可观测性：先给系统装上仪表盘

## 一、为什么这是第一步

V2 里为了搞清"37ms 花在哪"，我改了一次代码、跑了 6 轮压测、花了半小时，
最后只排除了一个嫌疑，还剩 30ms 不知道。

lag 多少？靠压测脚本里临时起 `for i in {1..300}; do lag; sleep 1; done`。
线程满没满？手动 `curl` 一下 actuator。
CPU 多少？`docker stats` 肉眼看。

**这些数据只在"我在压测"的时候存在，压测一停就没了。**
线上真出事，只有一堆日志。

## 二、装了什么，各自干什么

| 组件 | 一句话 | 干什么 |
|---|---|---|
| **Micrometer** | 应用内的台账 | 把 QPS、延迟、积压这些数字记下来，暴露成 `/actuator/prometheus` |
| **Prometheus** | 每 5 秒来抄一次账的人 | 定时抓取那个端点，存成带时间戳的序列（时序数据库） |
| **Grafana** | 画图 + 报警的 | 连 Prometheus，把序列画成曲线，配阈值告警 |

抓回来的原始数据长这样（纯文本，一行一个数字）：

```
miaosha_order_total{result="success"} 45231
miaosha_order_total{result="soldout"} 8812
tomcat_threads_busy_threads 12
kafka_consumer_fetch_manager_records_lag{partition="0"} 340
```

计数器只增不减，所以"每秒多少"要用两次采样的差值算——这就是 PromQL 里 `rate()` 干的事。

> **为什么不写脚本采**：脚本只在压测时有、不存历史、不能告警、多实例要自己拼。
> 脚本是体检，Prometheus 是心电监护仪。

## 三、埋了哪四个指标（这是重点，不是"装个监控"就完事）

Spring Boot 自带的 `http_server_requests` 只知道"这个 URL 花了多久"，
它不知道这一单是抢到了还是售罄、这 37ms 里 Redis 占多少、消费者落库成功了几单。

所以自己埋了四个：

| 指标 | 类型 | 埋在哪 | 回答什么问题 |
|---|---|---|---|
| `miaosha_order_total{result}` | Counter | `OrderService` | success / soldout / duplicate / **ratelimited** / send_fail / not_preheated 各多少 |
| `miaosha_redis_deduct_seconds` | Timer | `StockService.tryDeduct` | Lua 到底多快（V2 里那个"~0.1ms"是估的，没人量过） |
| `miaosha_kafka_send_seconds` | Timer | `OrderProducer.send` | **V2 那 5~6ms 的直接证据** |
| `miaosha_consumer_persist_total{result}` | Counter | `OrderConsumer` | ok / dup / short / bad_message / fail |

外加 Kafka 客户端的原生指标（`KafkaClientMetrics`），其中最重要的是：

```
kafka_consumer_fetch_manager_records_lag{partition="0"}   ← 还有多少单没落库
```

### 四个指标全部预注册

第一单还没发生的时候，这些计数器就以 0 出现在面板上。
不预注册的话，Grafana 上新实例的面板是空洞，很容易被误判成"没有流量"。

## 四、验证一：监控的数字，和已知答案对得上吗

这是**必须先做**的一步。一个标签写错、一次抓取失败、一个计数器名字打错，
面板上照样有漂亮的曲线，只是那条线是错的。

方法：拿一个已知答案去对——k6 说发了多少个请求，Prometheus 就应该数出多少个。

跑三次（3,000/s，30 秒）：

| 轮次 | k6 报的请求数 | Prometheus 计数差值 | 误差 |
|---|---|---|---|
| 1 | 89,353 | 89,353 | **0.00%** |
| 2（换 JVM） | 86,983 | 86,983 | **0.00%** |
| 3 | 87,947 | 87,947 | **0.00%** |

**三次全部一字不差。** 计数类指标可以信了。

> 复现：`make verify-metrics`

## 五、验证二：监控本身有没有拖慢系统

这个问题必须问。Prometheus 每 5 秒来序列化 1,666 行指标，
Grafana 还连着查，这些都是要花 CPU 的。

我先测到一版"监控开着 P99 115ms、关掉 17ms"，差点写成结论。
**但重跑一次，同样的配置是 17ms。** 说明那不是监控的锅。

真正的对照要在"每轮都干净"的前提下做：

| 场景 | QPS | P99（k6 客户端） | 丢弃 |
|---|---|---|---|
| 抓取**关**，排空后 | 2,999 | **17 ms** | 0 |
| 抓取**开**（5s 一次），排空后 | 2,996 | **18 ms** | 50 |
| 抓取**开**（5s 一次），排空后 | 3,000 | **13 ms** | 0 |

**结论：监控开销落在噪声里，测不出来。**

> 抓取一次耗时 17ms，5 秒一次 → 占用率 0.34%。如果这都能让 P99 涨 6 倍，
> 那说明系统本身离悬崖只有一步。真实原因见第七节。

## 六、踩到的四个坑（每个都会让面板"看起来正常其实在骗你"）

### 坑 1：`tomcat_threads_busy_threads` 根本不存在

装完监控，最关心的那条线程曲线是空的。原因是 **Spring Boot 3 默认关闭了 Tomcat 的 MBean 注册**，
而线程池指标是从 MBean 读的。

```yaml
server:
  tomcat:
    mbeanregistry:
      enabled: true     # 不开这个，就看不到线程池
```

**这条最阴**：不报错，不告警，只是那条线永远空白。

### 坑 2：`records_lag_max` 是 NaN

```promql
sum(kafka_consumer_fetch_manager_records_lag_max)   →  NaN
```

Kafka 在"还没有积压测量值"时把 `records-lag-max` 报成 NaN，一 `sum()` 全变 NaN，
排空判断逻辑直接死循环（我第一次跑就卡了 300 秒）。

真正能用的是**分区级**的：

```promql
sum(kafka_consumer_fetch_manager_records_lag)       →  75145   ✅
```

### 坑 3：`rate(...[15s])` 配 15 秒抓取 → 面板显示"无数据"

`rate()` 的窗口里至少要 2 个样本。窗口 15 秒、抓取 15 秒，
两个样本正好卡在窗口边界上，经常只落进 1 个 → 算不出来 → 空白。

**两个一起改**：抓取间隔降到 5 秒，查询窗口放到 30 秒以上。

### 坑 4：`lsof -ti :8080` 会把 Prometheus 一起杀掉

我想重启应用，执行 `kill $(lsof -ti :8080)`。
结果 Prometheus 也死了——因为它**正在抓取 8080**，那条连接也算在 `:8080` 上。

```
正确写法：lsof -ti tcp:8080 -sTCP:LISTEN
```

> 这个坑的价值：**"杀了该杀的"和"杀了正在用它的"是两件事。**

> 还有第五个坑在下面第七·补里：`-Xlog:jit+compilation` 被 JDK 17 静默忽略，日志 0 字节。
> 它和"Tomcat MBean 默认关闭"是同一类——**以为在记，其实什么都没记**。

## 七、意外收获 1：延迟数字的方差大得吓人

同一份代码、同一个到达率 3,000/s、同样的配置，P99 测出来是这样的：

| 场景 | P99 |
|---|---|
| 新启动的 JVM | **243 ms** |
| 同一 JVM，累计处理 ~18 万单 | 123 ms |
| 同一 JVM，累计 ~26 万单 | 165 ms |
| 同一 JVM，累计 ~35 万单 | 52 ms |
| 已经跑了几十万单的老 JVM（V2 的样本） | **13 ~ 18 ms** |

**19 倍的差距，全部来自"这台 JVM 跑过多少请求"。**

还发现另一个更大的：**应用放进容器后**（Docker VM 只有 4 核，和 MySQL/Kafka 抢），
同样 3,000/s，P99 是 **1,488ms**、丢弃 6,237 次；放回宿主机立刻回到 **17ms**。

> 这两条合起来说明一件事：**这套环境的延迟数字，只能同 JVM、同部署形态下横向比。**
> 这也解释了 V2 里那些 P99 为什么忽高忽低——我们一直没控制"预热程度"这个变量。
>
> 对 M2 的影响：找"容量拐点"时，必须先跑一轮热身丢掉，再跑正式那轮。

## 七·补、补测：预热曲线到底有多长（5 轮同一 JVM）

上一节只说"冷 JVM 更差"，没说清"多冷、多久热"。补一个受控实验：

**重启 JVM → 连续跑 5 轮，每轮 20 秒、3,000/s，每轮开始前等 Kafka 积压排空。**

| 轮次 | 这台 JVM 累计处理订单 | P50 | P95 | P99 | QPS | 丢弃 |
|---|---|---|---|---|---|---|
| 1 | 1 | 15 ms | 182 ms | **313 ms** | 2,825 | 3,472 |
| 2 | 56,531 | 7 ms | 30 ms | **92 ms** | 2,944 | 1,100 |
| 3 | 111,907 | 5 ms | 30 ms | **83 ms** | 2,970 | 593 |
| 4 | 174,840 | 5 ms | 8 ms | **12 ms** | 3,000 | 0 |
| 5 | 234,843 | 4 ms | 7 ms | **11 ms** | 3,000 | 0 |

**读法：横轴不是时间，是"这台 JVM 一共干过多少活"。**

```
313ms ──► 92ms ──► 83ms ──► 12ms ──► 11ms ──► 稳态
 冷              预热中                    ≥17 万单后
```

**结论：这台 JVM 要跑 15~17 万单（约 60 秒满负荷）才进入稳态。**

前 3 轮的丢弃（3,472 / 1,100 / 593）也是同一个原因：
延迟高 → VU 被占住 → `constant-arrival-rate` 发不出足量请求 → k6 记成丢弃。
**所以"丢弃"在这里不是压测机不行，是被测系统真的慢。**

### GC 能解释多少

同一个 JVM 的 GC 日志（`logs/gc.log`）：

| 时间 | GC 次数 | 累计暂停 |
|---|---|---|
| **第 0 分钟** | **56** | **346 ms** |
| 第 1 分钟 | 20 | 82 ms |
| 第 2~4 分钟 | 17 | 82 ms |
| 第 5 分钟 | 25 | 63 ms |
| 第 6~9 分钟 | 42 | 98 ms |

- 单次最长 **62.8 ms**，平均 4.2 ms
- **第 0 分钟就占掉全程 GC 时间的一半**——堆在长、分配率在爬坡

**GC 能解释一部分尾延迟，但解释不了 313ms。**
主因更可能是 JIT 分层编译（解释执行 → C1 → C2）加上连接池/线程池的惰性建立。

> 本想用 `-Xlog:jit+compilation` 直接数编译事件，结果**日志是 0 字节**——
> 这个 tag 写法被 JVM 静默忽略，不报错。这是又一个"看着在监控，其实什么都没记"的坑。
> 下次改用 `-XX:+PrintCompilation`。

### 对压测方法的直接影响

1. **正式测量前必须热身一轮并丢弃**，否则第一轮的数字没有可比性。
2. 横向对比只能在同一预热程度下做——现在是"≥20 万单之后"。
3. 这也解释了 V2 那组 13~18ms 为什么稳定：app 当时已经连续跑了 50 万单以上。

> 这组数据也画成了图：[m1-report.html](m1-report.html) 图 1。

## 八、意外收获 2：所有消息只进了同一个分区

清积压时重置消费位点，看到这个：

```
PARTITION 0  NEW-OFFSET 1832506
PARTITION 1  NEW-OFFSET 0
PARTITION 2  NEW-OFFSET 0
```

**三个分区，两个是空的。**

因为生产者发消息用的 key 是 `productId`，而这次秒杀只有一个商品 → 同一个 key
永远哈希到同一个分区 → 另外两个分区一条消息都没有。

于是：**3 个消费者，只有 1 个在干活，另外 2 个空转。**

这条把 V2 的"消费速率 950/s"解释完整了：

| 原因 | 贡献 |
|---|---|
| MySQL 单行锁 + 事务 | 主要因素，和 V1-b 一样 |
| **消息全在一个分区 → 消费并行度 = 1** | 就算把 MySQL 换掉，也还是一个消费者在跑 |

> **对 V4 的影响**：分桶（把库存拆成 N 行）必须同时改分区 key（如 `productId-bucketId`），
> 否则加了消费者也没用。这是这条观测最值钱的地方。

# M2 · 限流

## 一、实验 A：拐点到底在哪

### 为什么先做这个

V2 留下的说法是"3,000/s 干净、4,000/s 崩了"。但 4,000 那一轮 `dropped_iterations` 有 7,989，
说明**请求压根没发出去**，那个 P99 1,239ms 测的是压测机，不是系统。

所以第一步不是装限流，是**把 1,000 到 5,000 之间填满，看真实的曲线长什么样**。
限流阈值只能从这条曲线里读出来，不能拍脑袋。

### 方法

| 项 | 做法 |
|---|---|
| 档位 | 1,000 → 5,000，步长 500，共 9 档 |
| 每档时长 | 20 秒，`constant-arrival-rate` |
| VU 上限 | 到达率 × 2（给延迟上涨留余量） |
| 每档前 | 热身 3,000/s 20 秒（丢弃）→ 清空积压 → 重置库存 → 预热 → 1 单热身 |
| 重复 | 3,500 / 4,000 / 4,500 各重复 3~4 轮（单次不可信，M1 已经证明） |
| 采集 | k6 客户端指标 + Tomcat 忙碌线程（每秒采样，取中位与峰值） |

### 结果（每档取中位数）

| 目标 QPS | 轮次 | 实际 QPS | P50 | P95 | P99 中位 | P99 范围 | 线程 中位/峰 | 丢弃% |
|---|---|---|---|---|---|---|---|---|
| 1,000 | 1 | 1,000 | 4 | 8 | **12** | 12~12 | 6 / 12 | 0 |
| 1,500 | 1 | 1,500 | 4 | 7 | **10** | 10~10 | 10 / 13 | 0 |
| 2,000 | 1 | 1,999 | 4 | 8 | **12** | 12~12 | 12 / 64 | 0 |
| 2,500 | 1 | 2,499 | 4 | 7 | **10** | 10~10 | 11 / 20 | 0 |
| 3,000 | 1 | 2,997 | 4 | 8 | **12** | 12~12 | 17 / 39 | 0.1 |
| 3,500 | 4 | 3,498 | 4 | 8 | **22** | 16~55 | 23 / 32 | 1.1 |
| 4,000 | 3 | 3,911 | 5 | 11 | **34** | **13~132** | 28 / **200** | 4.1 |
| 4,500 | 3 | 4,489 | 5 | 13 | **32** | 28~46 | 28 / 157 | 1.1 |
| 5,000 | 1 | 4,879 | 5 | 12 | **79** | 79~79 | 32 / 151 | 2.4 |

逐轮明细和四张图见 [m2-experiment-a.html](m2-experiment-a.html)。

### 四个结论

**① 拐点不在 3,000，在 4,500~5,000 之间。**

- 1,000~3,000：P99 **10~12ms**，三条线（中位/最好/最差）完全重合 → 噪声极小，系统很轻松
- 3,500~4,500：中位 **22~34ms**，但范围拉开（16~132ms）→ 开始"贴着边界"
- 5,000：**79ms**、2.4% 丢弃、结束时积压 24,846 条排不完

**② 4,000 那一档是双峰的，这才是重点。**

三次跑：13ms / 34ms / **132ms**（那一轮线程顶到 200、丢弃 4.1%）。

同一个到达率，能跑出 10 倍差距。**说明 4,000 正好在"有时撑得住、有时撑不住"的边界上**——
这比一个确定的数字更有信息量：**容量不是一个点，是一条带。**

**③ V2 那个"4,000/s P99 1,239ms"要更正。**

这次 4,000 的中位数是 34ms。V2 那一轮 `dropped_iterations=7,989`，
**是 k6 发不出请求，不是系统慢**。当时没给足 VU，得出了错误的容量结论。

**④ 我又踩了一个自己挖的坑。**

为了省时间，我在重复实验里用"删 topic 再重建"来瞬间清空积压。
代价是：**消费者要重新加入消费组（rebalance），生产者要刷新元数据**，
正好撞上下一轮压测，就产生了那个 132ms。

事后用服务端指标核对才能看出来：那一轮服务端 P99 也是 68→135ms、线程 92——**服务端确实慢了，但不是容量的锅，是我的测量手段干扰了被测系统**。

> 教训：**为了省时间引入的"捷径"，本身就是新的变量。**

### 对 M2 阈值的决定

拐点是个区间（4,500~5,000），而 4,000 已经有双峰。所以限流阈值取 **4,000/s**：

| 候选 | 0 丢弃 | 最差 P99 | 选它的理由 |
|---|---|---|---|
| 3,000 | ✅ | 12ms | 太保守，浪费 25% 容量 |
| **4,000** | ⚠️ 曾出现 4.1% | 132ms | **取在双峰下沿，为噪声留余量** |
| 4,500 | ✅ 3/3 | 46ms | 数据更漂亮，但离 5,000 的崩溃点太近 |

**为什么不用 4,500**：它在 3 次里都干净，但 5,000 已经明确崩了。
两者只差 11%，而这个环境的噪声本身就有 10 倍波动——**在边界上押注等于没留余量**。

> 这个阈值的选择过程本身就是面试素材：
> "拐点不是一个点，是 4,500~5,000 的一条带；我取 4,000，因为 4,000 已经测到双峰，
> 说明它就在边界上下——这时候要的是余量，不是极限值。"

### 已知限制

1. **噪声和信号同量级**：4,000 以上，同一档两次跑能差 10 倍。要精确到 ±200/s 需要独立压测机。
2. **5,000 只跑了 1 轮**，且结束时积压没排完。
3. **删 topic 的捷径会引入 rebalance 干扰**，下次重复实验应改回"老实等排空"，或等 rebalance 稳定后再开压。

## 一·补、实验 A′：多一跳代理，到底要花多少

实验 A 是**直连应用**（k6 → 8080）。但实验 C 的三组都要经过网关，路径变了，
数字就不能直接跟 A 比。所以先单独量一次"只加代理、不加限流"的成本。

### 方法

| 项 | 内容 |
|---|---|
| 网关 | nginx 1.29.8，`listen 127.0.0.1:8000`，**不配 `limit_req`** |
| 上游 | `upstream miaosha { server 127.0.0.1:8080; keepalive 64; }` |
| 转发头 | `X-Real-IP`、`X-Forwarded-For`、`Host` |
| 档位 | 3,000 / 4,000，各多轮（每批第一轮丢弃：M1 证明首批一定慢） |
| 其余纪律 | 与实验 A 完全一致 |

### 结果（中位数）

| | P50 | P95 | P99 |
|---|---|---|---|
| 直连 8080 | **4 ms** | **8 ms** | 12~19 ms |
| 经网关 8000 | **5 ms** | **11 ms** | 15~66 ms |

- **P50 +1ms（4→5）、P95 +3ms（8→11）**：这是稳定的，8~10 轮都一致
- **P99 中位 16 → 34ms**：方向上"更差"是确定的，但波动 15~66ms，
  受环境噪声影响太大，**不能给准确倍数**

### 一条被自己推翻的假设

第一版我配了 `worker_processes 1`，看到 P99 涨到 38ms，怀疑是单 worker 排队。
改成 `auto`（8 核 8 worker）重跑：P99 中位反而没有改善（41ms）。

**结论：不是 worker 数的锅。** 撤回这个假设，配置保留 `auto`（那是正确做法，只是它不解释这个现象）。

### 一条真实的坑：0.026% 的 502（根因未定位）

67.5 万次请求里冒出 **176 个 502**，错误日志全部是同一句：

```
kevent() reported that connect() failed (54: Connection reset by peer)
    while connecting to upstream
```

`while connecting` 说明请求停在**TCP 建连阶段**，HTTP 一个字都没发出去——不是应用报错，是连接被重置。

**我先后给了三个解释，两个被自己的实验打脸：**

| 我的假设 | 验证方法 | 结果 |
|---|---|---|
| ① 长连接池复用了上游已关闭的连接 | 60s vs 15s 缓存，连续跑 | 都是 0，**测不出差异** |
| ② nginx 连接池是冷的，建连风暴 | 重启 nginx 让池清空，立刻打满 4,000/s | **0 个**，否定 |
| ③ Tomcat accept 队列溢出 | `netstat -s -p tcp` 看 `listen queue overflow` | **= 0**，否定 |
| ④ 空闲 40 秒后复用死连接 | 填池 → 空闲 40s → 再打 | 60s 配置 **0 个**，15s 配置 **5 个**——**和预测相反** |

**目前只能确定：**

- 176 个 502 集中在 3 个瞬间（10:19 / 10:26 / 10:29），都紧挨着 nginx 启动或 reload
- 之后 44 万次请求里一个都没有
- 全部发生在 `connect()` 阶段，应用侧没有任何 5xx
- 系统层 listen 队列溢出计数为 0

**判定：现象真实存在（0.026%），但机制未确认，现有的几个解释都不成立。**

> 这条记录的价值不在于"修好了"，而在于**演示了怎么证伪自己的解释**：
> 一个看起来非常合理的因果（nginx 缓存了死连接），换个方向一测就不成立。
> 如果只看"改完之后没再出现"，就会把它当成已解决。

**工程上的处理（缓解，不是根治）：**

```nginx
proxy_connect_timeout 2s;                    # 别让连接卡住 60 秒
proxy_next_upstream error timeout;           # 建连失败时重试一次
```

重试会把"偶发建连失败"从用户可见的 502 变成一次内部重试。
但要清楚：**这是在掩盖症状，不是消除原因。**

### 对实验 C 的影响### 对实验 C 的影响

**基线必须用 A′（经网关不限流），不能用 A（直连）。**
否则限流带来的任何改善，都可能只是抵消了代理开销。



## 二、实验 B：过载病历

### 要回答什么

实验 A 只说了"多少流量开始出问题"，没说"出问题时系统是什么样子"。
而这决定了限流到底要治什么病。

### 怎么打

| 项 | 值 |
|---|---|
| 到达率 | 6,000 / 8,000 / 5,000（分三次，各 60 秒） |
| 路径 | 直连 8080（B1）；经网关 8000（B2，作 C 的对照组） |
| 采样 | **每秒一次**（`ops/sampler.py`），压测后继续采 60 秒看恢复 |
| 记录 | 请求结果、忙碌线程、连接池、Kafka/Redis 耗时、积压、堆、CPU |

### 结果

| 场景 | 请求数 | 实际 | 成功 | 5xx | 丢弃 | P50 | P95 | **P99** | 最长 | 线程峰 | 堆峰 | KafkaP99 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 5,000 直连 | 297,010 | 4,950/s | 100% | 0 | 1% | 6 | 18 | **60** | 507 | **200** | 318MB | 19ms |
| 6,000 直连 | 359,240 | 5,987/s | **100%** | **0** | 0.2% | 6 | 12 | **24** | 100 | 119 | 267MB | 11ms |
| 6,000 经网关 | 359,249 | 5,987/s | **100%** | **0** | 0.2% | 7 | 16 | **32** | 91 | 133 | 268MB | 20ms |
| 8,000 直连 | 441,167 | 7,353/s | **100%** | **0** | **8.1%** | 9 | 202 | **323** | **1,009** | **200** | 315MB | 52ms |

### 预测全部落空

跑之前我写下的预测和实际：

| 项 | 预测 | 实际 |
|---|---|---|
| 完成率 | 85~95% | **100%** |
| P99 | 1~3 秒 | 24ms（6,000）/ 323ms（8,000） |
| 5xx | 会出现 | **0** |
| Kafka 发送 P99 | 几百毫秒 | 11~52ms |
| 恢复时间 | 10~30 秒 | **2~4 秒** |

**唯一说对的是"线程会钉在 200"——而且只在 8,000 和后来的 5,000 那两轮。**

### 为什么预测错：V2 的异步化改变了"过载"的形态

关键在这句：

```
请求路径上没有任何 MySQL 操作
  → 过载时不会有慢 SQL 把线程拖住
  → 请求一如既往地快速返回 200
  → 代价全部堆成 Kafka 积压
```

| 阶段 | 过载表现 | 用户感受 |
|---|---|---|
| V1（同步写库） | 线程等行锁 → P99 秒级 → 超时 5xx | **失败** |
| V2/V3（异步） | 请求照样成功 → **积压无限增长** | **越来越慢，但感觉不到** |

**这是最值钱的一条**：异步化把"过载"从**故障**变成了**隐性债务**。
8,000/s 跑 60 秒，积压 1,032,899 条，按 950/s 要排 **18 分钟**——
而用户那边看到的仍然是"下单成功"。

> 所以秒杀系统里最危险的指标不是错误率，是 **lag**。
> 错误率会提醒你，lag 不会。

### 崩溃的触发点是 GC，不是 Kafka 也不是 Redis

8,000 那轮，线程不是慢慢变多的：**前 45 秒平均只有 50 个，第 47 秒突然钉死在 200**。

同一时段的 GC：

| JVM 运行分钟 | GC 次数 | 累计暂停 |
|---|---|---|
| 850 | 110 | 344 ms |
| 851 | 80 | 226 ms |
| 852 | 110 | 312 ms |
| **853（压测那分钟）** | **391** | **1,752 ms** |
| 854 | 31 | 63 ms |

**GC 频率翻了 3.5 倍。** 堆峰值 315MB，而上限是 **384MB**（当初为容器写死的 `-Xmx384m`）。

链条是：分配率高 → 堆逼近上限 → GC 变密 → 每次 GC 暂停所有业务线程 →
请求变慢 → 占线程更久 → 线程池打满 → P99 爆炸。

**根因是一个配置选择（384MB 堆），不是架构问题。**

### 一个测出来的不稳定：5,000 也崩过

同样是 60 秒：6,000 只有 24ms，5,000 却有 60ms 且线程第 22 秒就钉死。

差别在于**跑的顺序**：5,000 那一轮开始时，Kafka 积压已经有 103 万条，
消费者满负荷写 MySQL；再加上堆已经接近上限。

**结论：4,000~6,000 之间不是"稳"，而是"看运气"**，取决于当下的 GC 状态和消费者负载。
只有 8,000 是确定性崩溃。

### 对 M2 的影响

1. **限流要治的不是 5xx，是延迟和积压。** 系统不会拒绝你，它会默默把你拖进 18 分钟的排队。
2. **C 实验的过载档位要用 8,000**，因为只有它能把"过载"稳定触发出来。
3. **阈值仍然取 4,000**：6,000 看起来更好，但 5,000 崩过一次，说明这段不稳；
   在"不稳的区间"里取上限，等于赌运气。
