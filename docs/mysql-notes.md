## 一、数据怎么存的：页与 B+ 树

### 为什么需要索引

`product` 表 10 万行，找 `id = 99999`。没有索引只能从第一行开始逐行比 —— 这叫**全表扫描**（`EXPLAIN` 里 `type=ALL`）。

索引 = **一份额外的、排好序的"值 → 数据在哪"的结构**。

代价：占空间 + 每次增删改都要同步维护它。**用"写变慢"换"读变快"。**

### 为什么是 B+ 树

| 方案 | 问题 |
|---|---|
| 有序数组 + 二分 | 插入要挪动后面所有元素 |
| 二叉树 | 1000 万行约 23 层，**每层一次磁盘 IO** |
| **B+ 树** | 一个节点 = 一页 = 几百上千个 key → 树很矮 |

> **理解 B+ 树的钥匙：数据库的性能瓶颈是磁盘 IO 次数，不是比较次数。**

### B+ 树的三条设计

**① 一个节点是一页（16 KB），不是一个数**

一页装几百上千个 key，每个节点有几百上千个分支，层数骤降。

**② 只有叶子节点存数据，上层只存 key**

上层只负责指路，同样空间能指更多路。

**③ 叶子节点之间用双向链表相连**

范围查询 `WHERE id BETWEEN 100 AND 200`，找到起点后顺着链表走，不用回根节点。

```
                   [ 50 | 100 ]              ← 根节点：只存 key，导航
                  /      |      \
          [10|20|30]   [60|70]   [110|120]   ← 中间节点：只存 key
           /   |   \     ...        ...
        ┌────┬────┬────┐
        │ 1  │ 10 │ 20 │  ...                ← 叶子节点：存真正的数据
        └────┴────┴────┘
          ↔    ↔    ↔                        ← 叶子之间双向链表
```

### 算一笔账：3 层能存多少行

| 项 | 值 |
|---|---|
| 一页 | 16 KB（有效约 15 KB） |
| 非叶子每个 key | 8 字节（BIGINT）+ 6 字节（指针）= 14 字节 |
| 一页能放多少 key | ≈ 1170 个 |
| 叶子每行假设 | 1 KB → 一页 16 行 |
| **3 层总容量** | 1170 × 1170 × 16 ≈ **2000 万行** |

**2000 万行的表，查任意一行最多 3 次页访问。** 而根节点和中间层通常常驻 buffer pool，所以实际磁盘 IO 往往只有 1 次。

### 全表扫描到底怎么扫

不是"一行一行读磁盘"，是**按页顺序读**：

```
读第 1 页（16KB）→ 页内逐行比较 → 读第 2 页 → ...
```

| 行大小 | 一页装多少行 | 10 万行要读几页 |
|---|---|---|
| 1 KB | 16 行 | 6,250 页 |
| 200 B | 80 行 | 1,250 页 |

**磁盘 IO 的单位是页，不是行。**

而且全表扫描是**顺序 IO**，磁盘最喜欢；走二级索引回表是**随机 IO**，每次都要寻道。这个差别是后面"为什么有时不走索引"的根因。

### buffer pool

读过的页缓存在内存里（我们的 compose 设为 512 MB）。小表能整个放进去，**第二次扫描接近纯内存操作**。

所以压测时"第一次慢、后面快"是正常的，V1 压测前必须**预热**。

## 二、索引的两种：聚簇与二级

### 聚簇索引（clustered index）

**主键索引的叶子节点存的是整行数据本身。**

```
聚簇索引（主键 id）
        ┌──────────────────────────────┐
        │ id=1 │ 测试商品 │ 99.00 │ 1000 │  ← 叶子 = 完整一行
        ├──────────────────────────────┤
        │ id=2 │ 商品B   │ 88.00 │ 500  │
        └──────────────────────────────┘
```

所以：**InnoDB 的表本身就是一棵按主键排序的 B+ 树。** 数据和索引是同一个东西。

三条推论：

1. **一张表只有一个聚簇索引** —— 数据只能按一种顺序物理摆放一次。
2. **主键 = 数据的物理摆放顺序**，不是"随便加的 id"。
3. **主键要短、要自增**：
   - 短：主键会被复制到每个二级索引的叶子里，越长所有索引越大
   - 自增：新数据总插在末尾，不页分裂；UUID 随机插入 → 页分裂 → 写放大

### 二级索引（secondary index）

**除了主键索引之外，所有索引都是二级索引。**

| | 聚簇索引（主键） | 二级索引 |
|---|---|---|
| 叶子节点存 | **整行数据** | **主键值** |
| 查一次要几次树查找 | 1 次 | **2 次**（回表） |
| 数量 | 1 个 | 多个 |

为什么二级索引不存整行？因为每个索引都存一份整行 → 空间爆炸 + 更新要同步所有索引。存主键最省，代价是回表。

### 自动 vs 手动

| 情况 | 是否自动建索引 |
|---|---|
| `PRIMARY KEY` | ✅ 聚簇索引 |
| `UNIQUE KEY` | ✅ 二级索引（唯一索引） |
| `FOREIGN KEY` | ✅ 二级索引（InnoDB 强制） |
| 普通查询列 | ❌ **必须自己建** |

```sql
-- 三种等价写法
CREATE TABLE product (..., KEY idx_name (name));
ALTER TABLE product ADD INDEX idx_name (name);
CREATE INDEX idx_name ON product (name);

SHOW INDEX FROM product;     -- Key_name / Seq_in_index / Column_name
DROP INDEX idx_name ON product;
```

**MySQL 不会因为你 WHERE 里用了某列就自动建索引。** 索引是开发者根据查询模式决定的。

## 三、回表的真实成本

### 501 次树查找

`name` 上有索引，`name='x'` 命中 500 行：

| 查询 | 树查找 | 回表 | 大致磁盘 IO |
|---|---|---|---|
| `SELECT *` | 1 + 500 = **501** | 500 次 | 最坏 **~500 次随机 IO** |
| `SELECT id, name` | **1** | **0** | **~1–2 次**（在内存则 0） |

`SELECT id, name` 之所以快：`name` 索引的叶子存的是 `(name, 主键)`，id 和 name 都在里面，**不回表**；而且 500 行 name 相同，在索引里连续排列，可能只占 1–2 页。

> 注意：不是"不用 IO"，是"**不用回表**"。索引页第一次访问也要读磁盘，只是大概率已在 buffer pool。

### 覆盖索引（covering index）

`EXPLAIN` 的 `Extra: Using index` 就是走了覆盖索引。

```sql
SELECT id, name FROM product WHERE name = 'x';   -- 覆盖索引 ✅
SELECT *        FROM product WHERE name = 'x';   -- 必须回表 ❌
```

**这不是"快一点"，是差 200 倍量级。**

### MRR（Multi-Range Read）

问题：二级索引按 `name` 排序，取出的主键是**乱序**的，回表就成了到处乱跳。

```
没有 MRR：8823 → 12 → 50031 → 7
         页551  页1   页3127  页1     ← 4 行 4 次随机 IO，页1 还被读了两次

有 MRR：先在内存排序 7, 12, 8823, 50031
         页1(id7) → 页1(id12 命中缓存) → 页551 → 页3127
         ← 3 次 IO，且地址单调递增
```

两个收益，别只看第一个：

1. **减少 IO 次数**（同页多行只读一次）
2. **把随机 IO 变成近似顺序 IO**（省寻道，可预读）—— 现实中往往这个更重要

生效条件：需要回表 + 命中行数较多 + `optimizer_switch` 里 `mrr=on`（默认开）。
代价：排序占内存（`read_rnd_buffer_size`，默认 256 KB）。
`EXPLAIN` 里显示 `Using MRR`。

## 四、怎么用索引：最左前缀

### 联合索引 = 按多列组合排序的一棵树

```
CREATE INDEX idx_ab ON product (a, b)
```

**不是"a 的索引顺便带上 b"，而是"按 (a, b) 排序的一棵树"**：先按 a，a 相同再按 b。

> **联合索引 `(a, b, c)` 可以当 `(a)` 用、当 `(a, b)` 用，但不能当 `(b)` 或 `(c)` 用。**

### 数据示例

| id | a | b | c |
|---|---|---|---|
| 1 | 10 | 20 | 30 |
| 2 | 10 | 15 | 50 |
| 3 | 5 | 99 | 10 |
| 4 | 10 | 20 | 10 |
| 5 | 5 | 1 | 99 |

`(a, b, c)` 索引内的顺序：

```
a=5  ─┬─ b=1  c=99  → id=5
      └─ b=99 c=10  → id=3
a=10 ─┬─ b=15 c=50  → id=2
      ├─ b=20 c=10  → id=4
      └─ b=20 c=30  → id=1
```

最终顺序：**5, 3, 2, 4, 1**

### 等值 vs 范围：谁打断有序性

| 条件 | a | b | c |
|---|---|---|---|
| `a=1` | 定位 | — | — |
| `a=1 AND b=2` | 定位 | 定位 | — |
| `a=1 AND b=2 AND c=3` | 定位 | 定位 | 定位 |
| `a>1 AND b=2` | 定位（范围） | **只过滤** | — |
| `a=1 AND b>2 AND c=3` | 定位 | 定位（范围） | **只过滤** |

**原因**：`a = 10` 精确定位到"b 有序的连续段"；而 `a > 5` 是很多段的拼接，**组内有序、组间无序**，b 没法二分。

> 最左前缀的准确表述：**只有等值条件能让后面的列继续走索引定位；范围条件会打断它。**

### ICP（Index Condition Pushdown）

`a>1 AND b=2` 里 b 虽然不能定位，但 MySQL 5.6+ 会把 `b=2` **下推到引擎层**在索引里过滤，减少回表次数。

`EXPLAIN` 显示 `Using index condition`。

**b 不能用来定位，但能用来减少回表** —— 两件事。

### 索引失效的四个常见原因

1. 列上套函数：`WHERE DATE(created_at) = '2026-11-02'`
2. 隐式类型转换：列是 BIGINT，却 `WHERE user_id = '123'`
3. 前缀通配：`LIKE '%abc'`
4. `OR` 两边的列有一边没索引

## 五、索引的取舍：优化器怎么算账

### 为什么有时明明有索引却全表扫描

10 万行、一行 1 KB ≈ 6250 页，查询命中 5 万行：

| 方案 | 代价 |
|---|---|
| 全表扫描 | 6250 次**顺序** IO |
| 走索引 | 50,000 次**随机** IO（回表） |

随机 IO 单次成本本来就高：机械盘是顺序的 50–100 倍，SSD 是 2–5 倍。

> **优化器的目标不是"用上索引"，是"总成本最低"。**

命中率大概超过 20–30% 时，优化器就会主动放弃索引。`EXPLAIN` 看到 `type=ALL` 但索引存在，就是这个原因，**不是索引失效**。

### 存储介质会改变选择

| 磁盘 | 随机/顺序成本比 | 优化器倾向 |
|---|---|---|
| 机械盘 | 1 : 50~100 | 更爱全表扫描 |
| SSD | 1 : 2~5 | 更爱走索引 |

同一条 SQL，本地 SSD 走索引、线上机械盘全表扫，完全可能。

### 建索引的纪律

1. 开慢查询日志（本项目 compose 已开，阈值 200 ms）
2. 找出慢 SQL
3. `EXPLAIN` 看 `type` / `key` / `rows` / `Extra`
4. 给 `WHERE` / `ORDER BY` / `JOIN` 的列建索引
5. **再跑一次，用数字证明快了**

索引不是越多越好：每多一个，写就多维护一棵树。单表一般 5 个以内。

命名建议 `idx_列1_列2`，别用 `idx`、`index1`。

## 六、事务：边界，不是命令

### 先分清两个维度

```
维度一：操作是什么？      SELECT / UPDATE / INSERT / DELETE
维度二：在什么边界里？    autocommit 单条 / BEGIN ... COMMIT
```

**事务不是一条命令，事务是一组命令的边界。**

### autocommit

```sql
UPDATE product SET stock = 999 WHERE id = 1;   -- 执行完立即提交，撤销不了
```

`autocommit = 1` 是默认值：每条语句自己就是一个事务。

### 显式事务

```sql
BEGIN;
UPDATE product SET stock = stock - 1 WHERE id = 1;
INSERT INTO orders (...) VALUES (...);
COMMIT;      -- 到这里才真正生效
-- 或
ROLLBACK;    -- 前面全部撤销
```

### ACID 在秒杀里的对应

| 字母 | 含义 | 对应 |
|---|---|---|
| A 原子性 | 要么全做要么全不做 | 扣库存和写订单不能只成功一个 |
| C 一致性 | 约束不被破坏 | 库存不能为负 |
| I 隔离性 | 并发事务互不干扰 | 两人同时下单不能互踩 |
| D 持久性 | 提交就永久生效 | 断电不丢 |

> **关键：事务保证"一起成功或一起失败"，不保证"你读到的数据在写之前没被别人改"。**

### 隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| READ UNCOMMITTED | 会 | 会 | 会 |
| READ COMMITTED | 不会 | 会 | 会 |
| **REPEATABLE READ（默认）** | 不会 | 不会 | 不会（间隙锁兜住） |
| SERIALIZABLE | 不会 | 不会 | 不会（太重） |

RC 与 RR 的真实差别：

- **RR**：ReadView 在事务**第一次快照读**时创建，整个事务都用它
- **RC**：**每次**快照读都新建 ReadView，能读到别人刚提交的

```sql
SELECT @@transaction_isolation;
```

## 七、两种读：快照读与当前读

| 语句 | 读哪个版本 | 加锁吗 | 术语 |
|---|---|---|---|
| `SELECT ...` | **快照**（历史版本） | ❌ 不加 | 快照读 |
| `SELECT ... FOR UPDATE` | 最新已提交 | ✅ X 锁 | 当前读 |
| `SELECT ... FOR SHARE`<br>`SELECT ... LOCK IN SHARE MODE` | 最新已提交 | ✅ S 锁 | 当前读 |
| `UPDATE` / `DELETE` | 最新已提交 | ✅ X 锁 | 当前读 |
| `INSERT` | —— | ✅ X 锁（+间隙） | 当前读 |

### 为什么 SELECT 能读到历史版本

InnoDB 每行保留多个历史版本（undo log）。开事务时拍个"快照"，之后普通 SELECT 都按快照挑版本 —— 这就是 **MVCC**。

```sql
-- 会话 A
BEGIN;
SELECT stock FROM product WHERE id = 1;   -- 1000
-- 会话 B
UPDATE product SET stock = 500 WHERE id = 1;  COMMIT;
-- 回到 A
SELECT stock FROM product WHERE id = 1;   -- 还是 1000（RR 快照读）
COMMIT;
SELECT stock FROM product WHERE id = 1;   -- 现在才是 500
```

### 超卖是怎么发生的

```
时刻   事务 A（用户1）              事务 B（用户2）
 t1    BEGIN
 t2    SELECT stock → 1000          ← 快照读，不加锁
 t3                                   BEGIN
 t4                                   SELECT stock → 1000
 t5    UPDATE stock = 999           ← 当前读 + X 锁
 t6    COMMIT
 t7                                   UPDATE stock = 999   ← 覆盖 A 的结果
 t8                                   COMMIT
```

**两单都成功，库存只减 1。** 问题不在 UPDATE，在**读的时候没锁**。

和 V0.1 的 `count++` 是同一个 bug：

| 内存 | MySQL |
|---|---|
| 读到 count = 100 | 读到 stock = 1000 |
| 算 101 | 判断 > 0 |
| 写回 | UPDATE 成 999 |
| 别人的写入被覆盖 | 别的订单被覆盖 |

### 修法：把判断塞进 UPDATE

```sql
UPDATE product
SET stock = stock - 1
WHERE id = 1 AND stock >= 1;
-- 影响行数 1 = 抢到；0 = 售罄
```

对应关系：

| 写法 | 相当于 |
|---|---|
| SELECT → 判断 → UPDATE | `count++`（错的） |
| `UPDATE ... WHERE stock >= 1` | `AtomicInteger`（单次原子） |
| `SELECT ... FOR UPDATE` | `synchronized`（先锁再说） |

## 八、锁：S 与 X

### 定义

| | 全称 | 别名 | 能做什么 |
|---|---|---|---|
| **S** | Shared Lock | 共享锁、读锁 | 只能读 |
| **X** | eXclusive Lock | 排他锁、写锁 | 能读能改 |

### 兼容矩阵

| 想加 ↓ / 对方持有 → | S | X |
|---|---|---|
| **S** | ✅ | ❌ |
| **X** | ❌ | ❌ |

**S 和 S 共存，X 跟谁都不共存。**

对应 Java 的 `ReentrantReadWriteLock`（读锁/写锁），同一个思想。

### 谁加什么锁

| 语句 | 锁 |
|---|---|
| `SELECT` | **不加** |
| `SELECT ... FOR SHARE` | S |
| `SELECT ... FOR UPDATE` | X |
| `UPDATE` / `DELETE` / `INSERT` | X |

### 关键澄清（面试常错）

**一行被 `FOR UPDATE` 锁住了，普通 `SELECT` 能读吗？**

**能。** 普通 `SELECT` 是快照读，**根本不申请锁**，跟任何锁都不冲突。但它读到的是**旧快照**。

```
事务 A: BEGIN; UPDATE stock=500 WHERE id=1;   ← X 锁，未提交
事务 B: SELECT stock WHERE id=1;              ← 能读，读到 1000
事务 B: SELECT ... FOR UPDATE;                ← 卡住
```

**锁限制的是"加锁的语句"，不是"所有读"。**

### 锁加在索引上，不是表上

1. X 锁加在**索引记录**上。
2. `WHERE` 列**没索引** → 全表扫描 → 扫过的每行都被锁 → **接近锁表**。
3. 所以给 WHERE 列建索引，不只是为了快，**更是为了锁的范围小**。

### 锁的类型

| 锁 | 锁什么 | 场景 |
|---|---|---|
| Record Lock | 一条索引记录 | `WHERE id = 1` |
| Gap Lock | 两条记录之间的空隙 | RR 下范围查询，防幻读 |
| Next-Key Lock | 记录 + 前面的间隙 | RR 默认 |
| 意向锁 IS/IX | 表级，表示"下面有行锁" | 加行锁时自动加 |

### S 锁升级死锁

```
事务 A: SELECT ... FOR SHARE   → S 锁
事务 B: SELECT ... FOR SHARE   → S 锁（兼容）
事务 A: UPDATE                 → 要升级 X，等 B 释放 S
事务 B: UPDATE                 → 要升级 X，等 A 释放 S
                                 ↑ 互相等 → 死锁
```

```
ERROR 1213 (40001): Deadlock found when trying to get lock
```

**实践原则：要么普通读（不加锁），要么 `FOR UPDATE`（一次拿 X）。别用 S 锁做"先读后写"。**

### UPDATE 的执行顺序

```sql
UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock >= 1;
```

```
① 走索引定位 id=1
② 加 X 锁            ← 加锁
③ 读最新值            ← 当前读
④ 判断 stock >= 1
⑤ 成立才改
⑥ 写 undo + redo
⑦ 提交释放锁
```

**② 在 ④ 之前**：即使库存为 0、条件不满足，这行也已经被锁过。RR 下锁可能持有到事务结束。

> 反直觉但重要：**"卖完了"不等于"没有锁竞争"。** V1-b 会实测到"库存扣到 0 之后 QPS 并没回升"。

## 九、乐观锁与悲观锁

| | V0.1 内存 | MySQL |
|---|---|---|
| 悲观锁 | `synchronized` | `SELECT ... FOR UPDATE` |
| 乐观锁 | `AtomicInteger`（CAS） | `version` 字段 / 条件更新 |

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 假设 | 一定会冲突 | 大概率不冲突 |
| 加锁时机 | 操作**之前** | 操作时不加，写入时校验 |
| 冲突少 | 慢（白加锁） | 快 |
| 冲突多 | 慢（排队） | 慢（大量失败/重试） |

### 写法一：version 字段

```sql
SELECT stock, version FROM product WHERE id = 1;   -- version=5
UPDATE product
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;
-- 影响行数 0 → 期间被别人改过
```

### 写法二：条件更新（秒杀用这个）

```sql
UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock >= 1;
-- 影响行数 0 → 售罄
```

### 关键差别：失败即返回 vs 重试

Java 的 CAS 是**重试循环**，冲突多会疯狂空转：

```java
while (!count.compareAndSet(old, old + 1)) { old = count.get(); }
```

SQL 的条件更新**没有重试循环**，返回 0 行直接返回"售罄"。**所以不会有重试风暴。**

### 为什么秒杀选乐观锁

| 考量 | 答案 |
|---|---|
| 冲突概率 | 极高 |
| 失败代价 | 很低（直接返回售罄） |
| 锁持有时间 | 一条语句（微秒）vs 整个事务（几十毫秒） |

**热点行场景下，锁持有时间比锁类型更致命。**

## 十、日志：为什么 UPDATE 快

| 日志 | 是什么 | 作用 |
|---|---|---|
| **redo log** | 物理日志，"某页某偏移改成什么" | 崩溃恢复，**先写日志再改页**（WAL） |
| **undo log** | 逻辑日志，"怎么改回去" | 回滚 + MVCC 历史版本 |
| **binlog** | 逻辑日志，"执行了什么 SQL" | 主从复制、归档 |

**为什么单行 UPDATE 快**：改的是内存里的页，顺序写一小段 redo 就返回，脏页后台异步刷。**所以瓶颈往往不在"写"，在锁等待。**

**为什么事务要短**：

1. 锁持有时间 = 事务长度
2. undo 不能回收 → 版本链变长 → 快照读变慢
3. 长事务拖住 purge 线程 → 磁盘涨

```sql
SELECT @@innodb_flush_log_at_trx_commit;   -- 1 = 每次提交刷盘，最安全
SELECT trx_id, trx_state, TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS 秒
FROM information_schema.innodb_trx ORDER BY 秒 DESC;
```

## 十一、连接与连接池

1. 一个连接 = 服务端一个**线程**，占内存、占调度。
2. `max_connections` 是硬上限（8.0 默认 151）。
3. 连接池不是越大越好：连接多了，锁竞争和上下文切换都上升。

HikariCP 经验公式：`连接数 ≈ CPU 核数 × 2 + 磁盘数`（4 核约 9~10 个）。
但**真实约束往往是锁竞争**：10 个连接全卡在同一行锁上，第 11 个没有意义。

V1 会看到：

```
HikariPool-1 - Connection is not available, request timed out after 30000ms
```

判断卡在哪：

| 现象 | 含义 |
|---|---|
| `Threads_running` 高 | CPU 在忙（真在算） |
| `Threads_connected` 高、`Threads_running` 低 | **都在等锁** |

```sql
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
SHOW VARIABLES LIKE 'max_connections';
```

## 十二、速查表

| 问题 | 答案 |
|---|---|
| 全表扫描怎么扫 | 按 16 KB 页**顺序**读叶子节点，页内逐行比较 |
| 为什么 B+ 树 | 一页装几百 key → 树矮 → 磁盘 IO 少 |
| 聚簇索引叶子存什么 | **整行数据** |
| 二级索引叶子存什么 | **主键值** |
| 回表成本 | **每命中一行一次随机 IO**（501 次树查找的例子） |
| 怎么免回表 | 覆盖索引（`Extra: Using index`） |
| MRR 做什么 | 主键排序后批量回表，随机 IO 变近似顺序 |
| 联合索引能怎么用 | `(a,b,c)` 可当 `(a)`、`(a,b)`，不可当 `(b)`、`(c)` |
| 为什么范围条件打断索引 | 组内有序、组间无序 |
| 有索引却全表扫 | 命中率太高，回表成本超过顺序扫描 |
| 事务是什么 | **一组命令的边界**，不是一条命令 |
| 事务能不能防超卖 | **不能**，它不管"读到的值有没有被改" |
| 普通 SELECT 加锁吗 | **不加**，快照读 |
| X 锁住了还能普通 SELECT 吗 | **能**，读到旧快照 |
| 锁加在哪 | **索引记录**上；WHERE 没索引 ≈ 锁表 |
| 乐观锁 vs 悲观锁 | 写入时校验 vs 提前锁住 |
| 秒杀为什么用乐观锁 | 锁持有时间短，失败即返回无重试风暴 |
| UPDATE 为什么快 | 改内存页 + 顺序写 redo |
| 为什么事务要短 | 锁、undo、purge 三重代价 |
