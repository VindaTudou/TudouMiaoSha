# V2 实验：把库存挪出 MySQL，瓶颈从请求侧搬到了消费侧

> V1 的结论是"所有请求都在争 MySQL 里同一行，吞吐封顶 950/s"。
> V2 要验证的是：**把库存判定挪到 Redis、把落库挪到 Kafka 之后，
> 请求侧能到多少？代价是什么？**
>
> 结论先说：请求侧从 950/s 提到 **3,000/s（P99 16ms，3 倍多）**，
> 但落库仍然卡在 **~950/s**——瓶颈没被消灭，只被**搬走了**。
>
> 配套：核心汇总表在 [../BENCHMARK.md](../BENCHMARK.md)，架构图在 [../architecture.md](../architecture.md)。

---

## 一、立项依据：V2 要修什么

V1 暴露出三个问题，V2 用三个设计分别对应：

| V1 的症状 | 根因 | V2 的设计 | 本文验证的实验 |
|---|---|---|---|
| 吞吐封顶 950/s | 所有请求抢 MySQL 同一行 | 库存判定挪到 **Redis + Lua** | 实验一 |
| 加压力只涨延迟 | 事务把锁从 UPDATE 持有到 COMMIT | 落库异步化，请求线程只发一条 MQ | 实验二、三 |
| 同一用户能下多单 | 判断和写入之间有缝 | Redis Set 去重，与扣减同一个 Lua 原子完成 | 第八节 |

注意第二行：**异步化不只是"把活挪走"，它直接缩短了持锁时间**——
这是 V1 里"裸 MySQL 2000 TPS、走事务只剩 950"那条推论给出的设计理由。

## 二、被测的东西

### 请求路径（三段，全程没有 MySQL）

```
POST /api/orders
   │
   ├─① Redis Lua：幂等检查 + 库存判断 + 扣减   ← 一次原子操作，~0.1ms
   │      返回 1 抢到 / 0 售罄 / -1 重复 / -2 未预热
   │
   ├─② 发 Kafka 消息（key = productId，保证同一商品进同一分区）
   │      发送失败 → 回滚 Redis → 返回 503
   │
   └─③ 立刻返回 200 {"status":"QUEUED"}
```

### 消费路径（真正的落库）

```
Kafka ──→ OrderConsumer ──→ OrderWriter.persist()  (@Transactional)
                               ├─ UPDATE product SET stock=stock-? WHERE id=? AND stock>=?
                               └─ INSERT INTO orders
                            手动 ack：成功才提交位点
```

**注意 `OrderWriter` 里保留了 V1-b 的条件更新。** 它现在只是兜底——正常路径下
Redis 已经判断过了，MySQL 这一层不会失败。但万一 Redis 数据旧了（比如重启恢复），
`WHERE stock >= ?` 保证 MySQL 里绝不会扣成负数。

> 这叫**纵深防御**：不指望上游一定对，下游自己再守一道。

### 三段关键代码

**① Lua 脚本：为什么必须是 Lua**

```lua
if redis.call('SISMEMBER', KEYS[2], ARGV[2]) == 1 then return -1 end   -- 幂等
local stock = redis.call('GET', KEYS[1])
if not stock then return -2 end                                        -- 未预热
if tonumber(stock) < tonumber(ARGV[1]) then return 0 end               -- 判断
redis.call('DECRBY', KEYS[1], ARGV[1])                                 -- 扣减
redis.call('SADD', KEYS[2], ARGV[2])                                   -- 记用户
redis.call('EXPIRE', KEYS[2], 86400)
return 1
```

Redis 单线程执行整个脚本，中间插不进任何别的命令。
**等价于 V0.1 里 `AtomicInteger` 的那一次 CAS，而不是 `count++` 的三步。**

如果拆成四条独立命令发过去，"GET → 判断 → DECRBY"之间照样有缝，V1 的超卖会在 Redis 上重演一遍。

**② 发送失败必须回滚**

```java
try {
    producer.send(msg);            // 同步等 broker ack，超时 3s
} catch (Exception e) {
    stock.rollback(productId, userId, quantity);   // 库存加回去、用户标记删掉
    throw new ServiceBusyException("下单繁忙，请重试");   // → 503
}
```

没有这一段，就会出现"库存扣了、消息没发出去"——**少卖**。
少卖不像超卖那样炸眼，但对账时一样是事故。

**③ 消费者：手动 ack，三种结局**

| 情况 | 动作 | 为什么 |
|---|---|---|
| 落库成功 | ack | 正常 |
| `DuplicateKeyException` | **ack** | 消息至少投递一次，订单号已经存在 = 已经落过库，跳过即可 |
| 其他异常 | **不 ack，抛出** | 让 Kafka 重投，不能丢单 |
| 消息体解析不了 | ack | 重投一万次也解析不了，别堵队列 |

### 语义变了：200 不再等于"下单成功"

| | V1 | V2 |
|---|---|---|
| 200 的含义 | 订单**已经在 MySQL 里** | 抢到名额，**正在排队** |
| 用户能否立刻看到订单 | 能 | 不能，要轮询 |
| 返回体 | 只有订单号 | `{orderNo, status:"QUEUED"}` |

**这是 API 契约的变更，不是实现细节。** 前端必须改成轮询 `/api/orders/{orderNo}`，
或者用 WebSocket 推送。很多"上了 MQ 之后用户说下了单查不到"的事故，根因就在这一步没改。

### 关键配置

| 配置 | 值 | 理由 |
|---|---|---|
| Redis `appendonly` | `yes`，`appendfsync everysec` | 它不是缓存，是**活动期间的账本**，丢了会超卖 |
| Redis `maxmemory-policy` | `noeviction` | 默认的 `allkeys-lru` 会**把库存 key 淘汰掉**——这是最容易踩的坑 |
| Kafka `acks` | `all` + 幂等 | 不能丢消息 |
| Kafka `linger.ms` | 5 | 攒批。**实测改 0 更差，见实验二** |
| Kafka 分区数 | 3 | 消费者并发度上限；同一商品进同一分区保证顺序 |
| 消费者并发 | 3 | 对应 3 个分区 |
| Tomcat `threads.max` | 200 | 默认值。**它决定了延迟上限，见实验二** |

### 故意留的口子

Redis 里的库存和 MySQL 里的库存是**两本账**。V2 没有对账任务，靠消费者兜底
+ 压测后人工对账。真正的生产系统需要一个定时对账 + 报警，这是 V3/V4 的事。

## 三、测试方法

### 和 V1 的三个不同

| | V1 | V2 | 不这么做会怎样 |
|---|---|---|---|
| 每轮开始 | 直接改 MySQL 库存 | **先 `POST /api/admin/preheat/1`** | Redis 里是上一轮的旧值，全测错 |
| 结果判定 | 200 / 409 / 5xx | **200 / 409 SOLD_OUT / 409 DUPLICATE / 其他** | 去重生效被算成"售罄"，结论反 |
| 结束判定 | 看到 QPS 就行 | **必须排空 Kafka 再对账** | 漂亮的 QPS 全是假的，单还没落库 |

第三条最关键：

```bash
# 压完先等 lag 归零，再数订单
lag_end=$(lag)
while [ "$(lag)" -ne 0 ]; do sleep 1; done
orders=$(mysql -e 'SELECT COUNT(*) FROM orders;')
```

**压测结束时 lag 可能是几万，那几万单还在 Kafka 里躺着。**
不排空就数订单，会得出"丢了 60% 的单"这种吓人的假结论。

### userId 必须绝对唯一

V2 按用户去重，用随机 ID 会撞车：

> 生日悖论：100 万个 ID 里随机抽 20 万次，**期望撞车约 2 万次**。
> 这些撞车会产生 409 DUPLICATE，污染"售罄"统计。

所以脚本用 `__VU * 10_000_000 + __ITER + 1`，VU 编号 × 一千万 + 迭代号，绝对唯一。

### 压测机自己会成为瓶颈——这次是决定性的

k6 的 `constant-arrival-rate` 靠 VU 发请求，**一个 VU 同时只能有 1 个在途请求**：

```
吞吐 = VU 数 ÷ 单请求延迟
```

延迟涨到 2 秒时，8,000 个 VU 最多只能推出 `8000 ÷ 2 = 4000/s`。
目标 8000/s，其余 4000/s 被 k6 记成 `dropped_iterations`。

**判断信号（三个同时出现）：**

1. `dropped_iterations > 0`
2. 应用侧不忙（CPU 低、连接池空闲）
3. `实际吞吐 × 延迟 << VU 数`

**所以本文所有超过 3,000/s 的数字都不可信**，下面会逐条标注。

## 四、实验一：请求侧容量扫描

每轮 15 秒，`stock=10000000`（保证不卖完，测最坏情况），单 SKU。

| 到达率 | 实际 QPS | P50 | P99 | k6 丢弃 | 可信吗 | 说明 |
|---|---|---|---|---|---|---|
| 1000 | 1000 | 4 ms | 20 ms | 0 | ✅ | 轻松 |
| **3000** | **3000** | **5 ms** | **16 ms** | **0** | ✅ | **可靠上限** |
| 4000 | 3333 | — | 1239 ms | 7,989 | ❌ | 压测机饱和，数据作废 |
| 5000 | 4924 | — | 107 ms | 890 | ⚠️ | 勉强，只能当下限 |
| 6000 | 5098 | — | 1037 ms | 7,697 | ❌ | 作废 |
| 8000 | 4805 | 1314 ms | 2029 ms | **42,791** | ❌ | 压测机先崩了 |

### 能确定的结论

> **请求侧至少能扛 3,000/s，P99 16 ms——是 V1-b（950/s）的 3 倍多。**

而且注意 3,000/s 这一行的 P99 **比 1,000/s 还低**（16ms vs 20ms）。
不是噪声，是**预热效应**：1,000/s 那一轮 Kafka 生产者是懒加载的，
第一次发送要建连接，被算进了 P99。后来每轮先下预热单，这个毛刺就消失了。

> **教训：压测前必须让所有懒加载组件跑起来**（连接池、Kafka producer、JIT）。
> 否则测出来的是"冷启动速度"，不是"稳态速度"。

### 3,000/s 以上为什么测不准

不是系统到顶了，是**同一台 Mac 上 k6 和被测系统抢 CPU**。
证据在第七节。

## 五、实验二：200 个线程能推出多少 QPS（含一个被推翻的假设）

### 先用 Little's Law 把账算清楚

```
在途请求数 L = 吞吐 λ × 单请求耗时 W
```

| 吞吐 | 单请求耗时 W | 在途请求 L |
|---|---|---|
| 3,000/s | 5 ms | **15 个线程** |
| 5,400/s | 37 ms | **200 个线程（Tomcat 上限）** |

**3,000/s 时只用了 15 个线程**，所以 P99 只有 16ms——离打满还远。
到 5,400/s 时线程已经顶到 200 的上限，每个请求平均占着线程 37ms，队列开始堆积，延迟爆到秒级。

> 复核方式：`curl -s localhost:8080/actuator/metrics/tomcat.threads.busy`
> 这个数顶到 200 且下不来，就是在排队。

**这就是 V3 限流阈值的由来**：既然 200 线程只能吃下 3,000/s 干净的量，
就别让 8,000/s 进来——进来的部分只会把所有人一起拖慢。

### 那 37ms 花在哪？先排除一个嫌疑

假设很自然：`linger.ms=5` 是**故意等 5 毫秒攒批**，改成 0 应该能降延迟。

**固定到达率 4000、固定 VU=2000、每组 3 轮取中位：**

| 配置 | QPS（中位） | P50 | P99 | 生产者队列等待 | 丢弃 |
|---|---|---|---|---|---|
| **`linger.ms=5`（保留）** | **3,894** | **5 ms** | **127 ms** | 5.3 ms | ~1,000 |
| `linger.ms=0` | 3,695 | 17 ms | **777 ms** | 5.8 ms | ~4,500 |

原始三轮：

```
linger.ms=5：3834/7ms/270ms · 3963/5ms/127ms · 3894/5ms/107ms
linger.ms=0：3695/125ms/777ms · 3922/7ms/211ms · 3580/17ms/1178ms
```

**三项指标全部变差。假设被推翻。**

### 为什么"立刻发"反而更慢

`linger.ms=0` 的含义不是"发得更快"，是**"每条消息单独发一次"**：

```
linger.ms=5：攒 5ms → 一次发 80 条 → 1 次网络往返 + 1 次 broker 处理
linger.ms=0：不攒     → 每条发一次   → 80 次网络往返 + 80 次 broker 处理
```

broker 请求数变成 80 倍，网络和 broker 的固定开销被一起放大。

> **这 5ms 不是成本，是投资。** 它换来的批量效果，远超它"等掉"的那点时间。

### 第二个发现（比第一个更值钱）

```
linger.ms=5  → 生产者队列等待 5.3 ms
linger.ms=0  → 生产者队列等待 5.8 ms   ← 关掉攒批，等待几乎没变
```

**如果这 5.3ms 是 linger 造成的，关掉它应该归零。但它没有。**

说明这 5~6ms 来自**发送线程排队 + 与 broker 的往返 + 等 ack**，不是那个攒批窗口。
我原来的推理链是错的：

```
❌ 错误推理：linger.ms=5 → 每条等 5ms → 5ms 是延迟大头
✅ 实际情况：5~6ms 是发送链路的固有开销，攒批反而在降低它
```

### 这一节排除了什么

| 环节 | 耗时 | 状态 |
|---|---|---|
| Redis Lua | ~0.1 ms | 待测 |
| Kafka 生产者队列 | 5~6 ms | 已测，**不是 37ms 的主要来源** |
| 其余 ~30 ms | ？ | **仍未定位** |

剩下的嫌疑：Kafka `get()` 在发送线程竞争下的实际等待（比队列时间更长）、
Tomcat 线程调度、JVM GC（堆只给了 384MB）、Docker 网络转发。

> **为什么停在这里**：再往下要改代码做消融（跳过 Kafka / 跳过 Redis），
> 即使找到，解法也是"异步发 + 本地消息表"，那是一个独立工程；
> 而真正的业务瓶颈（落库 950/s）一点没动。**性价比不划算，记录在案，留到 V4。**

## 六、实验三：消费侧到底多快

每轮压完，**等 lag 归零**，再数订单。

| 到达率 | Redis 扣减 | Kafka 消息 | 结束时 lag | 排空耗时 | 消费速率 | MySQL 订单 |
|---|---|---|---|---|---|---|
| 1000 | 15,001 | 15,001 | 2,444 | 3 s | 814 /s | 15,001 |
| 3000 | 45,000 | 45,000 | 35,300 | 36 s | **980 /s** | 45,000 |
| 8000 | 77,214 | 77,214 | 73,481 | 79 s | **930 /s** | 77,214 |

### 两条关键事实

**① 消费速率稳定在 ~950/s，和 V1-b 的单行热点吞吐一模一样。**

不是巧合。消费者干的事**就是 V1-b 干的事**：

```sql
UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?   -- 同一把行锁
INSERT INTO orders ...                                              -- 同一个事务
```

同一把行锁、同一个事务边界、同一个 `sync_binlog=1` 的 fsync。
**把活从请求线程搬到消费者线程，一行代码的耗时不会变短。**

> **这就是"异步"最容易骗人的地方**：它让**指标好看**（QPS 从 950 涨到 3,000），
> 但系统的**真实处理能力一点没涨**。多出来的全部堆在 Kafka 里。

**② 对账完全平。**

```
Redis 扣减 = Kafka 消息数 = MySQL 订单数（排空后）
三轮合计：137,215 = 137,215 = 137,215
```

零丢失、零重复、零超卖。

### 削峰的字面含义

```
上游：3,000/s 的洪水
下游：950/s 的小水管
中间：Kafka 这个水库
```

> **"削峰"不是让小水管变粗，是让洪水先灌进水库。**
> 水库能撑多久，取决于活动持续多长时间。

算一笔具体的账（库存 100 万、到达率 3,000/s）：

| 项 | 数值 |
|---|---|
| 洪水持续 | 333 秒 |
| 结束时积压 | **683,333 条** |
| 排空需要 | **719 秒 ≈ 12 分钟** |
| 占磁盘 | ~137 MB（每条约 200 字节） |

**磁盘完全不是问题，用户等待才是。** 秒杀结束 12 分钟后用户才收到订单短信，
这时候"抢到了吗"的客服电话已经打爆了。

> 所以 V2 的正确答案不是"Kafka 撑得住"，而是
> **"Kafka 撑得住，但业务撑不住——必须让下游变粗，或者让上游变细"**。
> 变细就是 V3 的限流。

## 七、实验四：压测机先崩了（证明 3,000/s 以上不可信）

怀疑 3,000/s 以上是环境问题，做了一次对照：**只加 VU，什么都不改。**

| VU 上限 | 目标到达率 | 实际 QPS | 结论 |
|---|---|---|---|
| 8,000 | 8,000 | 4,776 /s | 加 VU 前 |
| **40,000** | 8,000 | **5,609 /s** | VU 加 5 倍，QPS 只涨 17% |

**如果瓶颈在系统，加 VU 应该按比例涨；只涨 17%，说明卡在压测机这边。**

### 但这也证明了一件事：k6 报的数字是真的

同一轮里，服务端统计的请求数是 **86,770**，和 k6 自己报的请求数**完全相等**。

这说明：

- k6 说"我发了 86,770 个"，服务端确实收到了 86,770 个 → **k6 的统计没有撒谎**
- k6 说"我丢了 42,791 个" → 那是**真的没发出去**，不是发出去失败了

**两个数字互相印证的唯一办法，就是服务端独立数一遍。**
以后看到漂亮的 QPS，先问一句："服务端数过吗？"

### 还有一个没证实的疑点

8,000/s 那一轮里，单个请求耗时约 2.6~3.0 秒，**正好等于 Kafka 发送的 3 秒超时**。
看着像卡在发送上，但这一轮 `5xx` 是 0——如果真的超时了应该有 503。
**矛盾没解开，标记为未证实，不写进结论。**

> 记录一个想不通的现象，比编一个解释更诚实。

## 八、正确性

### 超卖：0

| 检查项 | 结果 |
|---|---|
| Redis 扣减总数 | 137,215 |
| MySQL 订单总数 | 137,215 |
| 库存为负 | 无（`WHERE stock >= ?` 兜底从未触发） |
| 同一用户多单 | 0（`409 DUPLICATE` 一次都没出现） |

### 幂等是怎么保证的（两层）

| 层 | 机制 | 防的是 |
|---|---|---|
| Redis | Lua 里 `SISMEMBER` + `SADD` | 同一用户连点两次 |
| MySQL | `uk_user_product(user_id, product_id)` | Redis 失效/重复消费时的最后一道 |

**为什么要两层**：Redis 的 `EXPIRE 86400` 意味着一天后 key 就没了，
但订单要永久存在。**去重集合是临时的，唯一索引才是永久的。**

### 被唯一索引抓出来的 bug

第一版订单号用「毫秒时间戳 + 4 位随机数」：

```
同一毫秒内并发 200 个请求 → 随机数只有 10000 个取值
→ 撞车 → Duplicate entry '...' for key 'orders.uk_order_no'
```

压测时表现为 0.02% 的 5xx，看起来像"压力太大偶尔失败"，
实际是**订单号生成器有 bug**。

改成 `AtomicLong` 自增 + 36 进制后复测：3,000 到达率跑 15 秒，11,991 单，异常 0、重复 0。

> **这个 bug 是被 `uk_order_no` 唯一索引抓出来的。**
> 没有唯一索引，就是脏数据躺在库里没人知道，等用户投诉"我下了一单显示两个订单号"。
>
> **唯一索引不是约束，是免费的断言。**

## 九、结论

### 一句话

> **V2 没有消灭 MySQL 的单行瓶颈，只是把它从请求路径上搬走了。**
> 请求侧从 950/s 提到 3,000/s+，但落库还是 950/s——多出来的全部堆在 Kafka 里。

### 完整因果链

```
① V1 瓶颈      所有请求抢 MySQL 同一行，950/s
      ↓
② V2 改造      库存判定 → Redis Lua（原子）
               落库      → Kafka 异步
      ↓
③ 请求侧结果   3,000/s，P99 16ms（3 倍多）
      ↓
④ 但代价       库存变成两本账，需要预热 + 对账
               API 语义变了：200 = 排队中，不是下单成功
      ↓
⑤ 消费侧真相   950/s —— 和 V1b 一模一样，因为它干的就是 V1b 的活
      ↓
⑥ 结论         "异步"提升的是吞吐指标，不是处理能力
               真实瓶颈还是单行锁 → V3 要限流 + 观测，V4 才谈分桶
```

### 三个被推翻/修正的认知

| 原本以为 | 实测 | 为什么错 |
|---|---|---|
| `linger.ms=0` 能降延迟 | P99 从 127ms **涨到 777ms** | 攒批不是成本是投资，关掉后 broker 请求数 ×80 |
| 生产者队列那 5.3ms 是 linger 造成的 | 关掉 linger 后仍是 5.8ms | 是发送链路固有开销，不是攒批窗口 |
| 上了 MQ 吞吐就上去了 | 请求侧上去了，落库一点没变 | 异步只是把队列从应用内存挪到了 Kafka |

### 面试版（30 秒）

> "V1 卡在 950/s，根因是所有请求抢 MySQL 同一行。V2 我把库存判定挪到 Redis，
> 用 Lua 把幂等检查、判断、扣减做成一次原子操作；落库改成发 Kafka 异步写。
>
> 请求侧从 950 提到 3,000，P99 16ms。但我压测时一定要等 Kafka lag 排空再对账，
> 结果发现消费速率稳定在 950/s——跟 V1 一模一样，因为消费者干的就是 V1 干的事，
> 同一把行锁、同一个事务。
>
> 所以 V2 的准确说法是：**瓶颈没被消灭，被搬到了下游**。请求侧的 QPS 是假象，
> 真正的处理能力还是 950。这就直接推出了 V3 要做限流——既然只能吃 3,000，
> 就别让 8,000 进来。"

### 四条常见追问

| 追问 | 答 |
|---|---|
| 为什么用 Lua，不用 Redis 事务（MULTI/EXEC）？ | MULTI 不能读中间结果做判断，`WATCH` 是乐观锁要重试；Lua 是服务端一次执行，最简单也最快 |
| Redis 挂了怎么办？ | 活动期间它是账本不是缓存，配了 AOF `everysec`；真挂了要停写并降级到 MySQL（V3 的降级预案） |
| Kafka 消息会不会丢？ | `acks=all` + 幂等生产者 + 手动 ack；落库失败不 ack 会重投，重复由 `uk_order_no` 挡住 |
| 消费速率只有 950，为什么不分桶？ | 分桶（把一行拆成 N 行，消费者按商品 ID 哈希取模）能到 ~9,500/s，但要用库存碎片和一致性换，V4 再做，先把 V3 的限流和可观测性补齐 |

## 十、已知限制（面试时要主动说）

| 限制 | 影响 |
|---|---|
| **k6 与被测系统同机** | 3,000/s 以上全是压测机的上限，不是系统能力。真实上限**未知**，只知道在 3,000~5,400 之间 |
| 应用在宿主机（8 核），MySQL 在容器（4 核） | 应用侧 CPU 偏乐观；V2 的瓶颈是 MySQL 单行，不影响结论 |
| Kafka / Redis 都是单节点，`replication-factor=1` | 没有高可用，V3 的故障演练只能做"进程挂掉"不能做"网络分区" |
| Redis 与 MySQL 没有自动对账任务 | 两本账的偏差只能靠人工查，V4 要补定时对账 |
| 37ms 里还有 ~30ms 没定位 | 只知道不是 linger，不知道是什么 |
| 数据全部单库单表 | 没有分库分表、没有读写分离 |

> **主动说出这些限制，比掩饰它们更能证明你真的做过实验。**
